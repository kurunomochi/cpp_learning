你将实现一个任务管理 REST API。浏览器、命令行工具或未来的前端应用都可以通过 HTTP 调用它。

操作 请求 成功结果

2. 一个 C++ 程序怎样变成可执行文件

2.1 先手动构建一次

打开 examples/01_hello.cpp：

cpp#include <iostream>
int main() {
    std::cout << "Hello, modern C++!\n";
}

在项目根目录使用 PowerShell：

powershellNew-Item -ItemType Directory -Force scratch | Out-Null
g++ -std=c++20 -Wall -Wextra -g examples/01_hello.cpp -o scratch/hello.exe
.\scratch\hello.exe

-std=c++20 选择语言标准；-Wall -Wextra 打开常用诊断；-g 放入调试信息；-o 指定输出文件。它们不会自动证明代码正确。

编译器驱动通常完成四个步骤：预处理展开 include 和宏；编译分析语言并产生汇编；汇编产生目标文件；链接把目标文件和库拼成可执行文件。你可以分开观察：

powershellg++ -std=c++20 -E examples/01_hello.cpp -o scratch/hello.ii
g++ -std=c++20 -S examples/01_hello.cpp -o scratch/hello.s
g++ -std=c++20 -c examples/01_hello.cpp -o scratch/hello.o
g++ scratch/hello.o -o scratch/hello.exe

.ii 很大是正常的：标准库头文件被展开了。.o 不是通常可以直接双击运行的程序；它可能仍有等待链接器解析的符号。

2.2 声明、定义和翻译单元

声明告诉编译器“存在一个叫这个名字、具有这种类型的东西”；定义提供函数体或对象的实际定义。

cpp// task_count.hpp
#pragma once
int task_count();

cpp// task_count.cpp
#include "task_count.hpp"
int task_count() { return 3; }

cpp// main.cpp
#include "task_count.hpp"
#include <iostream>
int main() { std::cout << task_count() << '\n'; }

把这三个文件放进自己的 scratch/multi 目录，在该目录执行 g++ -std=c++20 main.cpp task_count.cpp -o demo.exe。如果忘掉 task_count.cpp，编译 main 可能成功，但链接会提示 undefined reference。

每个 .cpp 连同它包含的头文件构成一个翻译单元。不要用 #include "task_count.cpp" 作为常规工程组织办法。应包含头文件，并让构建系统分别编译源文件。

2.3 为什么头文件不能随便放普通函数定义

如果两个 .cpp 都包含一个头文件，而头文件定义了同一个具有外部链接的普通非 inline 函数，链接时可能出现重复定义。这属于 ODR，即单一定义规则的范畴。

常见安排是：头文件放声明，源文件放定义。模板定义通常放在头文件中，让使用者实例化时可见。类体内定义的成员函数通常隐式 inline；inline 在这里关系到定义规则，不是“强迫编译器把函数展开”的命令。

#pragma once 防止同一个头文件在一个翻译单元里重复展开。它不能单独解决“多个翻译单元各自定义同一个普通函数”的问题。

现象 所处阶段 优先检查

F01. 从 main 的每个符号开始：声明、初始化与输出

你需要先建立的三个概念

源代码是写给编译器看的文本；程序是编译链接后的产物；进程是程序正在运行的一次实例。修改 .cpp 不会自动改变正在运行的旧进程。每次实验都要重新构建、停止旧程序、运行新程序。

对象是存放数据、具有类型和生命周期的实体。变量是我们命名对象的一种方式。int count{0}; 可以从左往右读成“创建一个名为 count 的 int 对象，并用 0 初始化”。不是先随便放一个东西、以后再决定类型。

文件：lessons/foundations/01_values.cpp

cpp#include <iostream>
#include <string>
int main() {
    int count{};                         // 初始化为 0
    const int limit{3};                  // 初始化后不再修改
    std::string title{"Learn C++"};      // 字符串对象拥有内容
    count = count + 1;                   // 给现有对象赋新值
    std::cout << title << '\n';
    std::cout << "count=" << count << ", limit=" << limit << '\n';
    return count == 1 ? 0 : 1;
}

逐行读懂：#include <iostream> 让当前翻译单元看到输入输出设施的声明；它不是运行时“导入另一个程序”。<string> 提供字符串类型。int main() 是普通控制台程序入口；空括号表示此形式没有参数；花括号圈定函数体。std:: 表示从标准库命名空间寻找名字。std::cout << ... 使用输出流的插入运算符，'\n' 是换行字符。大多数语句以分号结尾，函数体末尾不需要额外分号。

count{} 是值初始化，int 得到 0；count = count + 1 是赋值，左侧是被修改的对象，右侧先计算新值。const int limit{3} 仍然占有一个带类型的值，只是不能再通过这个名字修改。std::string 会管理自己的内存，不需要手动为结尾的零字符留位置。

预期输出：

最后的 条件 ? 值1 : 值2 是条件表达式。return count == 1 ? 0 : 1; 相当于“检查成功返回 0，否则返回 1”。注意 == 比较是否相等，= 执行赋值。main 的返回值交给操作系统；普通函数返回值交给调用者。

初始化不是一个无关紧要的风格问题

cpp// 片段

// int d;        // 自动存储期的内置整数没有被初始化，不要读取它
// int e{3.8};   // 故意错误：列表初始化拒绝这里的窄化

先普遍使用 {} 帮助防止意外窄化，但不要把它当万能语法：容器有 initializer_list 重载，std::vector<int> a{3, 7} 是两个元素 3 和 7，std::vector<int> b(3, 7) 是三个 7。遇到一个类型先看它选中了什么构造函数。

F02. 数字与表达式：类型决定计算结果

类型、范围和单位一起思考

bool 表示真假；char 表示一个字符编码单元；int 是常用整数；double 是常用浮点类型；std::int64_t 在提供它的平台上是恰好 64 位的有符号整数。不要把 int 一律当 32 位保证，查看 std::numeric_limits<int>；也不要把 long 当跨平台固定宽度整数。

后端中端口、任务 ID、字符串长度、时间各有范围和单位。即使都能存进一个整数，也不表示可以互换。例如 HTTP 的 Content-Length 是字节数，UTF-8 中文标题的字节数不等于显示字符数。

文件：lessons/foundations/02_numbers.cpp

cpp#include <cmath>
#include <iostream>
#include <limits>
#include <optional>
std::optional<int> checked_add(int a, int b) {
    const int high = std::numeric_limits<int>::max();
    const int low = std::numeric_limits<int>::min();
    if ((b > 0 && a > high - b) || (b < 0 && a < low - b))
        return std::nullopt;
    return a + b;                        // 检查通过后才执行加法
}
int main() {
    const int done{2};
    const int total{3};
    const double ratio = static_cast<double>(done) / total;
    const auto sum = checked_add(7, 5);
    const auto overflow = checked_add(std::numeric_limits<int>::max(), 1);
    std::cout << "integer=" << done / total << '\n';
    std::cout << "ratio=" << ratio << '\n';
    std::cout << "sum=" << sum.value_or(-1) << '\n';
    std::cout << "overflow=" << std::boolalpha << !overflow.has_value() << '\n';
    return sum == 12 && !overflow && std::abs(ratio - 2.0 / 3.0) < 1e-9 ? 0 : 1;
}

输出的关键值为 integer=0、ratio=0.666667、sum=12、overflow=true。2 / 3 两边是整数，先做整数除法，结果是 0；把结果赋给 double 也只能得到 0.0。先把一个操作数转换成 double，另一边才参与浮点运算。

static_cast<double>(done) 明确表达有意转换。强制转换不会自动检查越界，例如浮点转整数时仍要先保证可表示；不要为了消除警告随便加 cast。sizeof(T) 给的是对象大小，单位是 C++ 字节，一个字节有多少位可查 CHAR_BIT。

常见运算符及阅读顺序

表达式 含义 典型错误
a + b、a * b 算术 结果超出类型范围
a / b、a % b 商、整数余数 b 为 0；误把整数除法当小数
a == b、a != b 相等、不等 写成赋值
a < b、a >= b 大小比较 写 0 < x < 10
a && b、`a b`
!ok 逻辑取反 误以为 optional 的真假是内部 bool
++n、n++ 都使 n 加 1 同一表达式多次修改同一变量

区间应写成 x > 0 && x < 10。&& 左侧为 false 就不计算右侧，所以 pointer != nullptr && pointer->ready() 可以在右侧访问之前检查空指针；它不能保护悬空指针。优先级拿不准就加括号，避免写需要依靠细微求值顺序才能理解的表达式。

为什么必须在加法之前检查溢出

有符号整数溢出是未定义行为，不能先算出溢出结果再检查它。checked_add 的逻辑是：正数相加前检查 a > 最大值 - b；负数相加前检查 a < 最小值 - b。检查表达式本身也要在范围内。本例返回 optional<int>，有值表示成功，nullopt 表示无法表示；F11 会完整解释。

无符号整数按模运算也不等于业务合法。std::size_t size{0}; --size; 会绕到很大的值，所以不要用 i >= 0 配合无符号 i 写倒序循环。使用反向迭代器，或写 for (std::size_t i = values.size(); i > 0; --i) { use(values[i - 1]); }。

浮点不是十进制实数的精确替身。钱通常使用整数最小货币单位或合适的十进制库；容许误差比较要依据业务量纲和相对/绝对误差选择，例子的 1e-9 只是这个比值的测试阈值。

练习与参考：给 checked_add 增加最小值加 -1、最大值加 0、-7 加 5 三个调用，预期分别无值、最大值、-2。解释为什么把 static_cast<double> 移到整个 done / total 外面不能修正结果。F11 会用相同边界意识处理端口输入。

F03. 控制流：跟着状态一步一步执行

分支决定走哪一条路

cpp// 片段：score 已经是一个 int
if (score >= 90) {
    std::cout << "excellent\n";
} else if (score >= 60) {
    std::cout << "pass\n";
} else {
    std::cout << "retry\n";
}

从上到下检查条件，一旦命中就不进入后面的分支。通常保留花括号，即使暂时只有一行；否则以后加日志时容易把新语句放到条件之外。范围外输入应先拒绝，再做正常分类。

文件：lessons/foundations/03_control.cpp

cpp#include <iostream>
#include <vector>
int main() {
    const std::vector<int> ids{1, 2, 3, 4, 5};
    int sum{};
    for (const int id : ids) {
        if (id == 2) continue;           // 跳过当前这轮
        if (id > 4) break;               // 结束整个循环
        sum += id;
    }
    int retries{3};
    while (retries > 0) {
        --retries;                       // 循环状态必须能够前进
    }
    const bool accepted = sum == 8 && retries == 0;
    std::cout << "sum=" << sum << ", retries=" << retries << '\n';
    if (accepted) std::cout << "accepted\n";
    return accepted ? 0 : 1;
}

手工列出状态表比反复盯着代码更有效：

id 行为 sum
1 加入 1
2 continue 1
3 加入 4
4 加入 8
5 break 8

输出 sum=8, retries=0 和 accepted。continue 进入下一轮，break 退出最近一层循环；都不会直接退出 main。return 才退出当前函数。嵌套循环时，不要以为一个 break 会退出所有层。

三种循环怎样选

遍历容器优先 for (const auto& item : items)。需要下标时写普通 for；每轮先判断条件，再执行循环体，最后执行递增语句。while 适合“直到输入结束”；do ... while 至少执行一次，注意末尾分号。

cpp// 独立输入循环片段，需要 <iostream>、<string>
std::string line;
while (std::getline(std::cin, line)) {
    if (line == "quit") break;
    if (line.empty()) continue;
    std::cout << "received: " << line << '\n';
}

getline 读取一整行并去掉换行分隔符。不要先检查 eof() 再读取，EOF 状态通常是在读取失败后才被设置。std::cin >> number 遇到非法文本会进入失败状态，后续读取不会自动恢复；在 CLI 教学中先读整行再用 F11 的严格解析更容易控制错误。

如果混用 >> 与 getline，前者可能留下换行，后者马上读到空行；可以统一用 getline，或理解后用 ignore 清理。不要盲目把空行当用户真的没输入。

switch 适用于整数或枚举的离散值；每个 case 常用 break 结束。不写 break 会贯穿到后面的 case，需要这种行为时使用 [[fallthrough]]; 明确表达；std::string 不能直接作为 switch 条件。

练习：写一个循环接受 add、list、quit 三种命令，其余输出 unknown。先不存储任务。参考流程：getline → 判断 quit → 判断 add/list → 其他分支。输入结束时自然退出，不要 while(true) 后忘记 EOF 分支。完成后你已写出 CLI 主循环的骨架。

F04. 函数、作用域与契约：把问题拆成能验证的步骤

看函数时问四件事

输入是什么、结果是什么、是否修改外部对象、失败怎样表达。这四个问题就是一个小型契约。int add(int a, int b) 还没有说清楚允许多大的 a/b，因此真实输入需要边界规则。

文件：lessons/foundations/04_functions.cpp

cpp#include <iostream>
#include <string>
#include <string_view>
int increment_copy(int value) { return ++value; }
void increment(int& value) { ++value; }
bool valid_title(std::string_view title) {
    return !title.empty() && title.size() <= 200;
}
std::string make_label(int id) {
    return "task-" + std::to_string(id);   // 按值返回，结果有自己的生命周期
}
int main() {
    int count{3};
    const int changed_copy = increment_copy(count);
    const bool copy_unchanged = count == 3;
    increment(count);
    const auto label = make_label(count);
    std::cout << label << '\n';
    return changed_copy == 4 && copy_unchanged && count == 4 && valid_title(label) && !valid_title("") ? 0 : 1;
}

输出 task-4。调用 increment_copy(count) 时创建参数 value，它有自己的整数值。返回的 4 存进 changed_copy，原始 count 仍然为 3。increment(int& value) 的参数是调用者对象的别名，因此改变了 count。void 表示函数不返回一个结果值，不表示它没有效果。

valid_title 这里只检查非空及最多 200 字节，未实现最终服务的控制字符等完整规则；练习模型不要被误当生产校验。make_label 返回 string 值，调用者得到一个有自身生命周期的对象。这比返回局部变量引用安全。

局部变量能活到哪里

cpp// 故意错误：不要编译进正常项目
const std::string& broken() {
    std::string local{"gone"};
    return local; // 返回后 local 已销毁，引用悬空
}

作用域决定名字在哪里可见；生命周期决定对象什么时候存在。两者相关但不同：动态对象可以超过创建它的函数调用而存活；某个引用名仍可见时，被引用对象可能已经被销毁。F08 会用所有权描述这种差别。

名字被局部同名变量遮蔽也会制造误会；开启 -Wshadow 可以帮助发现。函数应短到能在脑中追踪局部状态，不要让“解析输入、写数据库、发 HTTP、打印日志”全部塞进同一个函数。

声明、重载与默认参数

cpp// 头文件中的声明片段
int clamp_count(int value, int maximum = 100);

// .cpp 中的定义片段：默认值通常只在声明处写一次
int clamp_count(int value, int maximum) {
    if (value < 0) return 0;
    return value > maximum ? maximum : value;
}

调用处需要先看见声明，链接时需要找到定义。函数可以按参数类型或数量重载，但不能只按返回类型重载。参数名称可以不同，类型、命名空间、const 等影响匹配的部分必须一致。默认参数在调用处使用，不是一个额外重载函数。

递归是函数直接或间接调用自己，需要终止条件，每次调用通常消耗调用栈。处理简单任务列表用循环更直接；不要为展示技巧引入深递归和栈耗尽风险。

练习：独立写 bool valid_limit(int value)，仅 1～100 返回 true。使用 -1、0、1、100、101 验证。参考实现：return value >= 1 && value <= 100;。然后拆出 .hpp/.cpp，故意漏编译 cpp 观察链接错误；这个实验连接主教材第 2 章和 CMake C04。

F05. 引用、指针、const、auto：先说明是否拥有和是否修改

文件：lessons/foundations/05_references.cpp

cpp#include <iostream>
#include <string>
int main() {
    std::string title{"draft"};
    auto copy = title;                   // 一个新的 string
    auto& alias = title;                 // title 的别名
    const auto& view = title;            // 不允许通过 view 修改 title
    copy += " copy";
    alias += " ready";
    std::string* pointer = &title;       // 保存地址，不拥有对象
    if (pointer != nullptr) pointer->append("!");
    pointer = nullptr;                  // 不会销毁 title
    std::cout << "copy=" << copy << '\n';
    std::cout << "original=" << view << '\n';
    return copy == "draft copy" && title == "draft ready!" && pointer == nullptr ? 0 : 1;
}

输出 copy=draft copy 和 original=draft ready!。把纸上画成两格：title 一格、copy 一格；alias 和 view 都画箭头指向 title，pointer 存储 title 的地址。把 pointer 设成 nullptr 只改变箭头，不影响 title。

同一个符号在不同位置有不同含义

写法 含义
int& ref = value 声明左值引用，绑定现有对象
&value 取地址
int* ptr = &value 声明指针并存入地址
*ptr 解引用，访问指向对象
ptr->member 等价于 (*ptr).member
a & b 整数按位与，和引用声明无关

引用必须初始化，之后不能改绑；ref = another 是给被引用对象赋值。引用本身没有正常的“空值”状态，但一样可能悬空。指针可以为 nullptr、可以改指向、可以悬空；非空不等于有效。访问前需要知道对象还活着，而不只是检查非空。

const 约束的是哪一层

cpp// 片段
int value{3};
const int* p = &value;     // 通过 p 不能修改 value，p 自身能改指向
int* const q = &value;     // q 不能改指向，通过 q 可以修改 value
const int* const r = &value; // 两方面都不允许

const 不意味着底层对象永不变化，例子中的 value 仍可经其他可写途径修改；也不意味着线程安全。不要用 const_cast 绕过接口约束，如果原对象确实是 const，再写它是未定义行为。

auto 不是“无类型变量”

auto 在编译期推导出固定类型。普通 auto x = expression 常会去掉顶层 const 和引用并创建值；需要引用就明确写 auto& 或 const auto&。例如 const int n{3}; auto a = n; 的 a 可以修改；const auto& b = n; 借用 n。

遍历 vector<Task> 时 auto task 每轮复制一个任务，修改它不会更新容器；auto& task 修改原任务；const auto& task 只读且避免复制。也不能一味避免所有复制：复制小整数、string_view 很便宜，按值返回结果常更安全。

函数参数的一套起点规则：小标量按值；较大对象只读时用 const T&；明确需要修改调用者用 T&；可选的非拥有对象可以用 T*；需要转移所有权时按值接收 unique_ptr<T>。不要把一个裸指针的出现自动解释成“应该 delete”。

练习与答案：把 F06 的 auto& title 改为 auto title，预期容器中的字符串不再增加 !，程序自检失败。再改成 const auto& 保留修改语句，预期编译失败，因为 append 操作需要可写对象。先预测，再操作。

F06. 数组、字符串与 vector：从长度和失效规则入手

文件：lessons/foundations/06_containers.cpp

cpp#include <array>
#include <iostream>
#include <string>
#include <vector>
int main() {
    const std::array<int, 3> ports{8080, 8081, 8082};
    std::vector<std::string> tasks{"read", "code"};
    tasks.push_back("test");
    for (auto& title : tasks) title += "!";
    for (const auto& title : tasks) std::cout << title << '\n';
    std::cout << "port=" << ports.at(0) << ", size=" << tasks.size() << '\n';
    return tasks.size() == 3 && tasks.at(1) == "code!" ? 0 : 1;
}

输出 read!、code!、test!，最后 port=8080, size=3。std::array<int, 3> 的元素数量是类型的一部分，创建后不变；std::vector<std::string> 的大小可在运行期改变。容器对象自身即使是局部变量，也可以管理另外分配的动态存储，不要把“局部变量”理解成“所有数据都必须在栈内”。

size、capacity、reserve、resize 要分清

cpp// 片段
std::vector<int> ids;
ids.reserve(10);  // 预留至少 10 个元素的容量，size 仍然是 0
// ids[0] = 1;    // 错误：不存在第 0 个元素
ids.push_back(1); // size 变为 1
ids.resize(3);    // size 变为 3，新增加的 int 元素值初始化为 0

operator[] 不负责边界检查，越界访问是未定义行为；.at(index) 越界抛出 out_of_range。性能敏感的已证明范围内循环可以用 []，外部输入索引需要验证。front()、back() 也要求容器非空。

vector 扩容时可能搬迁全部元素，先前拿到的引用、指针、迭代器因此失效。reserve 能减少搬迁，但不能承诺以后所有修改都安全；erase 会使删除位置及之后的迭代器/引用失效。不保存容器内部地址，改保存任务 ID 并重新查找，常更适合业务代码。

字符、字符串、字符数组不是同一回事

'a' 是 char，"a" 是含结尾零字符的字符串字面量数组，std::string{"a"} 是拥有内容的字符串对象。std::string 可以包含内部零字节，size 记录实际字节数量；交给只依赖结尾零字符的 C API 时可能被截断。

std::string_view 是非拥有视图，通常可理解为指针加长度。适合函数同步只读参数，不能延长字符串寿命。std::string_view v = std::string{"temporary"}; 在语句结束后会悬空。对 view 切片也不保证末尾有零字符，不能无条件把 view.data() 当 C 字符串。

原始数组 int items[3] 在很多表达式中会退化成指针，函数参数 int items[] 不携带数组长度。优先 array、vector；只读连续区间参数用 std::span<const int>，但 span 同样不拥有元素，也不能阻止生命周期结束。

map 与 unordered_map 什么时候再学

vector 适合连续遍历和小型任务列表；map 保持按键排序，常见查找复杂度对数级；unordered_map 平均常数级查找但不保证遍历顺序，最坏情况也不是常数级。map[key] 在 key 不存在时会插入默认值；只读查找使用 find/contains，避免查询动作改变数据。

练习：给 F06 删除最后一个元素，再验证 size 为 2；尝试 .at(10) 并捕获异常。参考：pop_back() 要求非空；异常使用 catch (const std::out_of_range& e)，e.what() 返回说明。不要为了“看看会怎样”在正常测试中执行 [] 越界。

F07. struct、class 与构造函数：让对象一直满足规则

数据对象和维护规则的对象

struct 与 class 的主要语言区别是默认成员访问权限和默认继承访问权限。可以用 struct 表达简单数据记录，用 class 隐藏不应随意改动的状态。它们都可以有构造函数、成员函数、析构函数和模板。

文件：lessons/foundations/07_classes.cpp

cpp#include <iostream>
#include <stdexcept>
#include <string>
#include <utility>
class Task {
public:
    explicit Task(std::string title) : title_(checked(std::move(title))) {}
    const std::string& title() const noexcept { return title_; }
    bool completed() const noexcept { return completed_; }
    void complete() noexcept { completed_ = true; }
    void rename(std::string title) { title_ = checked(std::move(title)); }
private:
    static std::string checked(std::string title) {
        if (title.empty()) throw std::invalid_argument("empty title");
        return title;
    }
    std::string title_;
    bool completed_{false};
};
int main() {
    Task task{"learn"};
    task.complete();
    bool rejected{false};
    try { task.rename(""); }
    catch (const std::invalid_argument&) { rejected = true; }
    std::cout << task.title() << ": " << std::boolalpha << task.completed() << '\n';
    return rejected && task.title() == "learn" && task.completed() ? 0 : 1;
}

输出 learn: true。公开函数形成对象可使用的操作；private 成员阻止调用者直接把 title_ 改为空串。构造函数没有返回类型，它先初始化成员，随后才执行函数体。explicit 阻止这里某些隐式转换；你仍可以明确写 Task{"learn"}。

const std::string& title() const noexcept 分为三段：返回类型是只读引用；函数后面的 const 说明不通过 this 修改普通成员；noexcept 声明异常不应逃出。返回引用只在 Task 及其成员仍有效期间可用；不能把临时 Task 的 title 引用长期保存。

初始化列表和赋值的差别

title_(checked(std::move(title))) 在成员创建时提供初始值。若在函数体里写 title_ = title;，则 title_ 已先默认构造，再被赋值；const 成员、引用成员和无默认构造的成员尤其需要初始化列表。

成员实际按类内声明顺序初始化，与初始化列表的书写顺序无关。成员析构顺序相反。让列表保持与声明一致，避免依赖尚未初始化的成员。

不变量与失败后的状态

本例的不变量是“title_ 不为空”。构造失败时不会产生一个可供调用者使用的无效 Task；rename 先检查新的字符串，再赋值，所以非法改名不会破坏旧标题。测试先调用非法改名，再确认标题还是 learn，验证的就是这个性质。

static 成员函数没有 this 指针，因此 checked 不直接访问某一个 Task 的成员。this 指向当前对象；同名参数可能遮蔽成员，所以示例通常用尾部下划线区分成员变量。

暂时不要急着把所有东西改成继承

服务器“拥有一个仓库”用成员对象表达，是组合。若以后需要不同仓库实现可以再考虑抽象接口。用基类指针销毁派生对象时基类通常需要 virtual 析构函数；把派生对象按值传给基类参数会发生切片。当前项目主要依赖组合，理解这些坑即可，不必先建复杂继承树。

练习：给 Task 增加 reopen()，使 completed_ 变为 false，并增加成功后检查。再把标题规则加强为不超过 200 字节。参考：在 checked 中增加边界检查，构造和 rename 同时获得相同规则；不要在两个地方复制一份校验。

F08. 生命周期、RAII、复制与移动：资源必须有明确的负责人

从析构顺序观察资源管理

文件：lessons/foundations/08_lifetime.cpp

cpp#include <iostream>
#include <memory>
#include <string>
#include <utility>
struct Trace {
    explicit Trace(std::string label) : label(std::move(label)) {
        std::cout << "open " << this->label << '\n';
    }
    ~Trace() { std::cout << "close " << label << '\n'; }
    Trace(const Trace&) = delete;
    Trace& operator=(const Trace&) = delete;
    std::string label;
};
int main() {
    Trace outer{"outer"};
    {
        auto first = std::make_unique<Trace>("resource");
        auto second = std::move(first);  // 转移指针的所有权，不移动 Trace 对象
        if (first || !second) return 1;
        std::cout << "owner moved\n";
    }                                   // second 析构，释放 Trace
    std::cout << "leaving main\n";
}                                       // outer 析构

预期输出依次为：

textopen outer
open resource
owner moved
close resource
leaving main
close outer

outer 在 main 的局部作用域中；first/second 在内部作用域中。内部作用域结束时 second 的析构函数释放它拥有的 Trace 对象，first 已经没有对象。注意 std::move(first) 没有把 Trace 移到另一个内存位置，而是把 unique_ptr 的所有权转给 second。

RAII 的核心是把资源的获取与释放绑定到对象生命周期。对象正常离开作用域或因异常展开栈时，其已构造完成的成员和局部对象会被清理。异常前尚未完成构造的对象不会调用自己的完整析构函数，但已成功构造的子对象会清理。

这不覆盖断电、强制杀进程、std::abort 等所有退出方式；数据库持久化和事务另有责任。C++ 没有自动保证你任意写的资源管理代码都正确，因此尽量让标准库对象做拥有者。

自动存储期、动态存储期和所有权

局部 string、vector、unique_ptr 离开作用域自动析构；它们可以拥有动态分配的资源。手工 new 得到的对象若没有匹配释放会泄漏；两次 delete 是错误。优先直接放对象，只有需要动态生命周期等理由才使用 make_unique。裸指针和引用主要表达借用，借用者不负责 delete。

文件同样可用 RAII：std::ifstream input{"config.txt"}; 构造时打开，析构时关闭。打开失败通常要检查流状态，默认不会自动抛异常。mutex 则由 lock_guard 在作用域内持锁，异常路径也会解锁。

复制和移动不是两个速度按钮

复制通常创建独立的逻辑值；移动允许目标接管源对象的资源。std::move(x) 只是把表达式转换为可参与移动重载选择的形式，本身不搬运资源；如果没有合适的移动操作，也可能发生复制。

unique_ptr 的移动后状态明确为空；string/vector 的移动后对象通常仍有效但状态未指定，除非某个操作有更强保证。不要断言“所有移动后的字符串一定为空”。可以销毁、重新赋值，调用其他操作时必须满足其前置条件。

const std::string source; std::move(source) 得到 const 右值，常见 string 移动构造不能接收可修改资源的 const 源，因此可能选择复制。不要到处加 std::move，尤其返回本地对象常直接 return value;，让复制消除/隐式移动机制工作。

Rule of Zero 与自定义析构的代价

让成员使用 string、vector、unique_ptr 等正确的资源拥有者，通常无需自己实现复制、移动、析构，这叫 Rule of Zero。只要自己开始管理裸资源，就必须一起审视复制构造、复制赋值、移动构造、移动赋值和析构，即 Rule of Five。

示例 Trace 删除复制，是为了避免读者误以为打印 open/close 的模拟资源可以随便复制。最终仓库也删除复制，因为一个连接不应该被两个对象误以为自己独占关闭。

shared_ptr 表达共享所有权，用引用计数决定何时释放；计数控制块支持多线程并不意味着被管理对象的成员线程安全。互相持有 shared_ptr 会形成环，可使用 weak_ptr 表达不拥有的观察关系。没有共享生命周期需求时不使用它。

练习：在输出 owner moved 后抛出 runtime_error，并在 main 的外层 try/catch 接住，预测 close 行的顺序。参考：内部资源先清理，再清理 outer（若 outer 位于该 try 内），最后进入 catch。异常练习放到临时副本，不改默认必须返回成功的测试。

F09. 迭代器、算法与 lambda：读懂回调的关键准备

文件：lessons/foundations/09_algorithms.cpp

cpp#include <algorithm>
#include <iostream>
#include <string>
#include <vector>
struct Task { int id; std::string title; bool done; };
int main() {
    std::vector<Task> tasks{{3, "test", false}, {1, "read", true}, {2, "code", false}};
    std::ranges::sort(tasks, {}, &Task::id);
    const int wanted{2};
    const auto it = std::ranges::find_if(tasks, [wanted](const Task& task) {
        return task.id == wanted;
    });
    if (it == tasks.end()) return 1;
    it->done = true;
    const auto removed = std::erase_if(tasks, [](const Task& task) { return task.done; });
    // erase 后不再使用 it，它可能已经失效。
    std::cout << "removed=" << removed << ", left=" << tasks.size() << '\n';
    return removed == 2 && tasks.front().id == 3 ? 0 : 1;
}

输出 removed=2, left=1。Task 是简单聚合，花括号按字段顺序初始化。sort 的 {} 表示默认比较器，&Task::id 是成员指针形式的投影，表示按 id 比较。不是对指针地址排序，也不是每次排序都复制一个容器。

迭代器是位置，end 是边界

begin 指向第一个元素，end 指向最后一个元素之后的位置。区间写成 [begin, end)，左闭右开；空容器 begin 等于 end。find_if 返回 end 表示没找到，在判断前不能 *it 或 it->title。不能因为程序某次没崩溃就认为解引用 end 合法。

erase_if 返回删除的数量。传统 remove_if 只把保留元素往前重排并返回逻辑末端，不缩小容器；搭配 erase 才真正改 size。C++20 的 erase_if 更直接，仍必须遵守失效规则。

lambda 按“捕获、参数、函数体”拆开

cpp[wanted](const Task& task) { return task.id == wanted; }

[wanted] 把 wanted 的值保存进闭包；const Task& task 是每次算法调用给它的参数；函数体返回匹配与否。lambda 可以理解成带有 operator() 的匿名函数对象。它能携带状态，因此适合网络路由回调。

[&wanted] 借用外部 wanted，外部对象必须活得更久。[] 不捕获局部变量；[=] 按值隐式捕获，[&] 按引用隐式捕获。教学和长期保存的回调优先显式列出捕获，便于审查生命周期。捕获 this 保存的是指针，不会延长当前对象寿命。

默认 lambda 的按值捕获成员不能在函数体中修改；mutable 允许修改闭包内部副本，并不会因此修改原始值。需要返回闭包时可用 auto 返回类型；std::function 是一种类型擦除包装，可能带来分配和间接调用，并非所有 lambda 都必须放进去。

ranges 的惰性不是缓存

cpp// 片段，需要 <ranges>；tasks 必须在整个遍历期间有效
auto pending = tasks | std::views::filter([](const Task& task) { return !task.done; });
for (const auto& task : pending) std::cout << task.title << '\n';

view 通常在遍历时筛选，不一定提前生成新容器；它可能借用原容器。不要返回借用本地 vector 的 view。遍历期间修改底层容器、修改影响筛选的字段，需要认真查看迭代器和视图规则；初学时优先先计算、后修改。

练习与参考：改为保留未完成任务并统计数量；用 count_if 可以统计而不删除，循环统计也可以。说明 HTTP 中的 [&repository] 为什么要求仓库活到所有请求处理结束，这就是从算法回调走向服务器回调的连接点。

F10. 模板、头文件与命名空间：看懂库的声明

文件：lessons/foundations/10_templates.cpp

cpp#include <concepts>
#include <iostream>
#include <string>
#include <utility>
template<class T> class Box {
public:
    explicit Box(T value) : value_(std::move(value)) {}
    const T& get() const noexcept { return value_; }
private:
    T value_;
};
template<std::integral T> constexpr bool positive(T value) {
    return value > T{0};
}
static_assert(positive(3));
static_assert(!positive(-1));
int main() {
    const Box<std::string> title{"templates"};
    const Box<int> id{7};
    std::cout << title.get() << ": " << id.get() << '\n';
    return positive(id.get()) ? 0 : 1;
}

输出 templates: 7。template<class T> 表示定义一个类型参数，Box 与 Box 是不同的类型；这里的 class 也可以写 typename，不要求 T 一定是用户定义的 class。value_ 的类型在具体实例化时确定，不是在运行时随便变化。

普通函数与函数模板

把 T 替换为具体类型可以帮助初学阅读，但编译器的真实处理包含名称查找、约束检查等规则，不是简单文本替换。模板类型推导可能无法在多个不同参数类型间选出一致的 T；不要把所有失败都用强转盖住。

template<std::integral T> 限制 T 满足整型概念。它比无约束模板产生更贴近使用要求的错误。positive(1.5) 会因约束不满足而编译失败；这是预期的接口保护。concept 检查表达式和类型条件，不会自动证明业务意义或线程安全。

constexpr 表示在满足条件的上下文中可以常量求值，普通运行期输入仍然可以调用。static_assert 在编译期要求条件为真，和运行时 assert 不一样。const 主要限制修改，不保证某个值一定能用于编译期计算。

模板定义通常放头文件

使用点常需要看见模板定义才能实例化。如果只在头文件声明 Box 的成员，把所有模板实现藏到普通 cpp，另一个翻译单元使用新类型时可能出现链接错误。显式实例化可以为固定类型解决部分问题，但初学时先把小模板完整定义放头文件。

头文件要自包含：使用 string 就包含 string，不依赖使用者碰巧先 include 别的头。普通非 inline 函数定义放 cpp，避免重复定义；模板和类内定义的成员函数有相应的规则允许头文件组织。头文件全局变量可使用 C++17 inline 变量或 extern 声明加 cpp 定义，不能随意重复定义。

#pragma once 是常见编译器支持的写法；传统 #ifndef include guard 是另一种。它们防止同一翻译单元重复包含，不会把多个 cpp 自动变成一个翻译单元。

命名空间、enum class 与别名

cpp// 片段：可放在 domain.hpp 的 namespace task 内
enum class Status { pending, done };
using TaskId = std::int64_t; // 需要 <cstdint>；别名不是新的独立强类型

枚举使用 Status::pending，避免名字混进外部作用域。不要在公共头文件中写 using namespace std;，否则会改变所有包含者的名称查找环境。cpp 内匿名命名空间可隐藏只供当前翻译单元使用的辅助实现。

练习：把 Box 放进 box.hpp，用两个 cpp 分别实例化 Box 和 Box，一起链接。故意调用 positive(1.5) 阅读第一条约束诊断，再恢复。参考：不需要在 CMake 中为每个模板实例添加一个 target，两个 cpp 作为同一 executable 的源文件即可。

F11. optional、异常和严格输入：错误是接口的一部分

文件：lessons/foundations/11_errors.cpp

cpp#include <charconv>
#include <iostream>
#include <optional>
#include <string_view>
#include <system_error>
std::optional<int> parse_port(std::string_view text) {
    if (text.empty()) return std::nullopt;
    int value{};
    const auto [end, error] = std::from_chars(text.data(), text.data() + text.size(), value);
    if (error != std::errc{} || end != text.data() + text.size()) return std::nullopt;
    if (value < 1 || value > 65535) return std::nullopt;
    return value;
}
int main() {
    for (const auto input : {"8080", "80x", "0", "65536", "", "99999999999999999999"}) {
        const auto value = parse_port(input);
        std::cout << '[' << input << "] -> ";
        if (value) std::cout << *value << '\n';
        else std::cout << "invalid\n";
    }
    return parse_port("8080") == 8080 && parse_port("65535") == 65535 &&
        !parse_port("80x") && !parse_port("0") && !parse_port("65536") &&
        !parse_port("") && !parse_port("99999999999999999999") ? 0 : 1;
}

只有 [8080] -> 8080 成功，其他展示输入都输出 invalid。解析必须满足三层条件：语法转换成功、整个输入被消耗、数值处于业务范围。80x 前缀能转成 80，不等于输入是合法端口。

from_chars 返回结束指针和 error code，示例用结构化绑定 const auto [end, error] 拆开。它不会像部分流输入那样自动跳过前导空格，也不会接受所有习惯写法；本课程有意使用严格十进制语法，正号、空白等接受策略需要主动设计。

optional 的真假是“有没有值”

cpp// 片段，需要 <optional>
std::optional<bool> completed{false};
if (completed) {
    // 能进入这里，因为它有值；*completed 才是 false
}

nullopt、值 false、值 true 是三种不同状态，恰好适合 PATCH：不传 completed 不修改，传 false 取消完成，传 true 标为完成。先检查存在再 *optional；.value() 在无值时抛 bad_optional_access；value_or(default) 返回实际值或默认值，不适合所有错误都静默吞掉的场景。

什么时候用异常

用户输错端口很常见，optional 能直接表达失败；构造数据库仓库打不开文件时，无法形成有效对象，抛异常可以沿调用栈交给边界处理。当前 C++20 项目没有使用 C++23 的 std::expected；不需要为了读教材先升级标准。

cpp// 片段，需要 <exception>、<iostream>
try {
    run_server(); // 需要你自己的声明与实现
} catch (const std::exception& error) {
    std::cerr << error.what() << '\n';
    return 1;
}

按 const 引用捕获，避免复制和切片。具体异常的 catch 放一般异常之前。异常跨越作用域时清理局部资源，所以 RAII 与异常配合；不要每层都 catch 后返回“成功”。HTTP 边界应把已知输入错误映射到适当状态码，内部异常记录日志并返回一般错误，避免把 SQL/文件路径暴露给客户端。

noexcept 不是“忽略异常”：异常逃出 noexcept 函数会触发终止。析构函数应避免抛异常，尤其已经在异常展开时；资源关闭失败需要单独的显式操作/日志策略，而非任意在析构中 throw。

文件读写也要检查结果

cpp// 片段，需要 <fstream>、<string>、<stdexcept>
std::ifstream input{"settings.txt"};
if (!input) throw std::runtime_error("cannot open settings.txt");
std::string line;
while (std::getline(input, line)) {
    // 在此验证每一行，不把“读到字符串”当作配置合法
}
if (input.bad()) throw std::runtime_error("read failed");

相对路径按当前工作目录解析，不是按 cpp 文件位置解析；这是 tasks.db “不见了”的常见原因。重要输出还需检查写入/flush/关闭结果，不能只因文件曾成功打开就认为数据一定保存成功。

练习：给 parse_port 加入 " 80"、"+80"、"-1"、"1" 和 "65535"，预期前三者无值，后两者成功。再把它改成返回 optional 的正 ID 解析器。比较主教材的 parse_id，关注拒绝输入的规则，而不只看函数名称。

F12. 从语法读到服务器：对象关系、线程与学习验收

先用一个可结束的小程序理解共享状态

文件：lessons/foundations/12_threads.cpp

cpp#include <iostream>
#include <mutex>
#include <thread>
#include <vector>
int main() {
    int count{};
    std::mutex mutex;
    {
        std::vector<std::jthread> workers;
        for (int n = 0; n < 4; ++n) {
            workers.emplace_back([&count, &mutex] {
                for (int i = 0; i < 1000; ++i) {
                    std::lock_guard lock{mutex};
                    ++count;
                }
            });
        }
    }                                   // jthread 析构并 join，之后才能读取 count
    std::cout << "count=" << count << '\n';
    return count == 4000 ? 0 : 1;
}

输出 count=4000。count 和 mutex 比 workers 活得更久；线程闭包按引用捕获它们。每个线程执行 1000 次，四个线程理论上应得到 4000，但普通 ++count 是读、修改、写，不是天然原子操作。没有同步的并发访问构成数据竞争时，程序是未定义行为，不能只说“偶尔少加几次”。

lock_guard 构造时锁定，退出本轮作用域时解锁。一个锁保护的是约定的共享状态，所有访问者必须遵守约定；只给写入一侧加锁而读取不加，不会自动正确。本例最终读取发生在全部 join 后，已经没有工作线程在改它。

jthread 析构时请求停止并 join；本例工作函数没有接收 stop_token，所以不会因请求停止而提前结束，而是做完有限循环。若线程无限循环且不响应停止，析构仍可能一直等待。join 是等待完成，不是强行杀线程。

把陌生的真实声明逐段翻译

cpp// 摘自配套仓库的接口形式
[[nodiscard]] std::optional<Task> get(std::int64_t id);

[[nodiscard]] 提醒调用者不要随意丢弃结果；optional 表示任务可能不存在；Task 是按值返回的数据；int64_t 是 ID 类型。这个接口没有引用 HTTP 请求对象，所以仓库可以在核心测试中直接使用。

cpp// 概念片段：学习读捕获关系，完整路由见 src/http_api.cpp

3. 重新整理你已经学过的变量、引用和函数

3.1 优先初始化，让对象从第一刻就有效

cppint count{};                 // 0
bool completed{false};
std::string title{"CMake"};
// int broken{3.14};         // 窄化转换，编译拒绝

未初始化的局部基础类型可能带来未定义或其他错误行为。不要靠“我机器上打印出来刚好是 0”判断。花括号初始化有帮助，但要认识容器的 initializer_list：std::vector<int> a(3, 7) 是三个 7；std::vector<int> b{3, 7} 是两个元素 3 和 7。

3.2 值、引用、指针分别表达什么

cppvoid observe(const std::string& title); // 借用，只读，不复制整段字符串
void rename(std::string& title);       // 借用，允许修改调用方对象
void consume(std::string title);       // 自己拥有一份值，可从调用方复制或移动

小整数、布尔值通常按值传递。大对象只读时可用 const 引用。如果函数要保存一份数据，按值接收再移动到成员有时更简单。不要机械地把所有参数都写成 const T&。

引用必须绑定到对象，使用期间对象必须仍然存在。指针还能表达“没有对象”的情况，所以需要判空。二者都不自动拥有对象；不要看到 T* 就认定需要 delete。

cppstd::string make_title() {
    std::string result = "Learn C++";
    return result; // 返回值，安全；允许返回值优化
}
// 错误示意：不要返回局部变量的引用或指针。
// const std::string& bad() { std::string x = "x"; return x; }

3.3 const 和 auto 的实用判断

const 表示不能通过这个名字直接修改该对象。它不是“整个对象世界都不可变”，也不是并发同步机制。

cppstd::string original = "A";
auto copy = original;         // 新的 string
auto& alias = original;       // 引用
const auto& view = original;  // 只读引用
alias = "B";                 // original 和 view 看到 B；copy 仍是 A

auto 会推导类型，不是动态类型。特别留意 auto 默认不保留引用，auto& 才明确借用。遍历容器时 for (const auto& task : tasks) 通常能避免复制每个任务。

3.4 整数、边界和外部输入

数据库 ID 使用 std::int64_t。容器的 size() 常返回无符号类型；混用有符号值要留意负数变成很大的正数。

不要拿 atoi("12abc") 这类宽松转换当接口验证。std::from_chars 给出错误码和停止位置，本项目同时检查这两项：

cppstd::int64_t value{};

if (error != std::errc{} || end != text.data() + text.size() || value <= 0) {
    return std::nullopt;
}

"12abc" 即使读出了 12，仍然必须拒绝，因为没有消费完整输入；特别大的数字必须检查超出范围。完整代码在 src/domain.cpp，函数还会拒绝正负号和空串。

4. 类与对象：先维护数据的规则，再考虑继承

4.1 struct 与 class

它们最主要的语言区别是默认访问权限和默认继承权限。不要把 struct 当成“不能有方法的 C 结构体”。

本项目的 Task 是简单数据载体：

cppstruct Task {
    std::int64_t id{};
    std::string title;
    bool completed{false};
};

三个字段可直接阅读；没有必要为每个字段写一套没有约束作用的 getter/setter。数据库连接则有更强的规则：成功构造后必须持有有效连接，不能随意复制，这更适合 class 封装。

4.2 构造函数与成员初始化列表

cppclass UserName {
public:
    explicit UserName(std::string text) : text_(std::move(text)) {
        if (text_.empty()) throw std::invalid_argument("empty user name");
    }
    const std::string& text() const noexcept { return text_; }
private:
    std::string text_;
};

这个片段需要 <string>、<utility>、<stdexcept>。初始化列表直接构造成员；构造函数体执行时，成员已经初始化。成员的初始化次序按类中的声明顺序，不是列表中的书写顺序。

explicit 避免不想要的隐式转换。成员函数最后的 const 表示它不通过 this 修改普通成员。noexcept 是不抛异常的承诺；承诺被违反会触发终止，不是“自动忽略错误”。

4.3 组合优先，继承按需

服务器包含仓库，仓库拥有数据库连接；这都是“有一个”的组合关系。只有确实要表达可替换的接口时才引入继承，例如未来的 TaskStore 接口可以同时有 SQLite 和内存实现。

如果你通过基类指针删除派生对象，通常需要虚析构函数：virtual ~TaskStore() = default;。把派生对象按值复制给基类会发生对象切片。入门阶段不需要为了“看起来面向对象”把每个函数都改成虚函数。

4.4 错误使用应尽量在编译阶段阻止

cppTaskRepository(const TaskRepository&) = delete;
TaskRepository& operator=(const TaskRepository&) = delete;

连接和互斥量不适合被随意复制。删掉复制操作，能让错误的 auto second = repository; 直接编译失败。它比在注释中写“请不要复制”更可靠。

练习：给 TaskRepository 写一个复制语句，观察错误，然后删除它。验收：能区分“数据值可以复制”与“资源拥有者不可随意复制”。

5. RAII、智能指针与移动语义

5.1 资源不仅是内存

资源包括文件、socket、数据库连接、prepared statement、锁和线程。它们都有“获得”和“释放”操作。手工在函数末尾释放时，提前 return 和异常往往会漏掉清理。

RAII 的做法是让对象拥有资源，在构造或初始化时建立所有权，在析构时释放。正常离开作用域和异常展开都会析构已经完成构造的自动对象。

cpp{
    std::lock_guard lock(mutex);
    // 这里持有锁；即使下面抛异常，离开作用域也会释放锁
    update_shared_state();
}

上面是机制片段，mutex 与函数需要由调用代码定义。先理解“对象生命周期绑定资源生命周期”，再记具体类名。可延伸阅读 C++ Core Guidelines 的资源管理章节。

5.2 unique_ptr 表达唯一所有权

cppauto owner = std::make_unique<Task>(Task{1, "Learn ownership", false});
auto* borrowed = owner.get(); // 借用，不接管所有权
auto next = std::move(owner);

移动后 owner 为空；next 拥有原对象。只要 next 仍然拥有它，borrowed 仍指向那一个对象；next 释放对象后 borrowed 就悬空。智能指针不会神奇地修复所有借用指针的生命周期。

std::move 本身主要做类型转换，使表达式可以被选择为移动来源；实际搬移资源的是被调用的移动构造/赋值操作。对不支持移动的类型，写了 move 也不一定发生资源转移。

一般的标准库对象移动后应视为有效但状态未指定，除非该类型明确给出更强保证。不要把 unique_ptr 移后为空的特性套到所有类型。

5.3 C API 资源也能用 RAII 包起来

SQLite 通过 C API 给出 sqlite3*，我们给 unique_ptr 提供一个自定义清理器：

cppstruct DatabaseCloser {
    void operator()(sqlite3* db) const noexcept;
};
std::unique_ptr<sqlite3, DatabaseCloser> db_;

实现中调用 sqlite3_close_v2。这样，构造函数打开连接后即使设置参数失败，已经归 unique_ptr 所有的句柄仍会被关闭。SQLite 打开失败时也可能返回非空句柄，所以先交给拥有者管理，再检查错误码。接口语义见 SQLite 打开连接文档。

SQL statement 同样使用 unique_ptr 加 sqlite3_finalize 清理器。因为局部 statement 在成员数据库之前销毁，我们不会让 statement 引用一个已销毁的连接。

5.4 shared_ptr 不是默认答案

只有多个所有者确实需要共同决定生命周期时才用 shared_ptr。它会维护引用计数；shared_ptr<A> 中的 A 不会因此自动线程安全。A 持有 B、B 又持有 A 的强引用会形成环，可能需要 weak_ptr。

本项目把请求计数器放在 shared_ptr 中，是让注册进服务器的回调共同持有它。数据库仓库没有这个需求：main 中仓库寿命长于 server，回调只借用它。

5.5 Rule of Zero 与异常安全

能由 string、vector、unique_ptr 等成员完成资源管理时，不要手写一堆复制、移动、析构函数，这叫 Rule of Zero 的设计方向。必须直接管理原始资源时，再认真处理全部特殊成员操作。

异常安全至少应保证资源不泄漏、对象仍处于有效状态；“强保证”进一步要求失败后状态如同操作未发生。数据库事务是另一层机制：C++ RAII 能释放句柄，但不会自动把多条 SQL 组合成一个原子业务操作。

练习：写一个只打印“构造/析构”的小类，在作用域中抛出异常，在外层 catch，观察析构顺序。验收：能解释为什么析构函数通常不该抛异常。

6. 字符串、容器、optional 与算法

6.1 string 拥有内容，string_view 借用内容

std::string 存储字符序列。std::string_view 通常只保存指针和长度，不拥有字符。它适合短时间只读参数，例如 title_error(std::string_view)。

cppstd::string storage = "Learn CMake";
std::string_view view = storage;
// storage 销毁、重新分配或相关范围失效后，view 不能继续使用。

不要返回指向临时 string 的 string_view。不要以为 view.data() 必定以 \0 结尾；它可能只是字符串中间的一段。本项目调用 from_chars 时显式传入首尾指针。

UTF-8 下 std::string::size() 统计字节，不是屏幕上字符数。本项目明确限制标题为 1～200 个 UTF-8 字节；HTTP JSON 解析器验证输入的 UTF-8，领域层只检查字节长度、ASCII 控制字符和纯 ASCII 空格。全角空格、字素簇等更复杂的 Unicode 规则是后续扩展，不要误称当前规则是“最多 200 个汉字”。

6.2 vector 是第一个应该熟练的容器

vector 连续存储元素，按下标访问快、尾部追加常用。扩容可能搬迁元素，从而使旧引用、指针和迭代器失效。reserve 预留容量，resize 改变元素数量，两者不同。

cppstd::vector<Task> tasks;
tasks.reserve(100); // size 仍是 0
tasks.push_back({1, "Read", false});

删除 vector 元素后，删除位置及其后的迭代器和引用可能失效。不要一边 erase 一边盲目递增旧迭代器。

std::map 按键排序，std::unordered_map 通常用哈希查找。不要先背哪一个永远更快；根据遍历顺序、键数量、内存和测量结果选择。本项目 CLI 用 vector，服务端查询交给数据库。

6.3 optional 表达“可能没有结果”

cppstd::optional<Task> found = repository.get(42);
if (found) {
    std::cout << found->title;
}

没找到任务是正常业务结果，用 nullopt 表达；数据库损坏是另一类失败，用异常表达。不要把二者都塞进“返回空对象”。

std::optional<bool> 特别值得练习：if (patch.completed) 检查是否有值，并不是检查值是否为 true。所以包含 false 的 optional 仍进入分支，这使 {"completed": false} 能正确撤销完成状态。

std::variant 表示若干类型中的一种，适合明确的多种结果；访问时可用 std::visit。它与 optional 的定位不同：optional 是“有值/无值”，variant 是“具体是哪一种”。

6.4 算法、lambda、投影

cppauto it = std::ranges::find(tasks, wanted_id, &Task::id);
if (it != tasks.end()) it->completed = true;

第三个参数是投影：拿每个 Task 的 id 与 wanted_id 比较。找不到时得到 end，必须先判断，不能直接解引用。

cppauto it = std::ranges::find_if(tasks, [wanted_id](const Task& task) {
    return task.id == wanted_id;
});

lambda 可以理解为带着必要上下文的可调用对象。[wanted_id] 拷贝值，[&repository] 借用外部对象，[token = std::move(api_token)] 把一个值移动进回调自身。

对于保存下来以后才执行的回调，不要默认使用 [&] 捕获一切。函数返回后局部变量可能已经消失。服务器中的路由回调正是这种需要认真检查生命周期的场景。

6.5 span 与 ranges view

std::span<const int> 可以以统一方式借用数组或连续容器的一段数据。它不拥有内存，不自动延长生命周期，C++20 的普通下标操作也不是保证抛异常的边界检查。

std::views::filter 构造惰性视图，一般不会立即复制出新的容器。视图依赖原范围的有效性；底层容器修改或销毁后不要继续使用旧视图。调试复杂流水线困难时，直接写清楚的循环完全可以。

运行 lab02_modern，预期最后一行 count=4000。练习：添加两个任务，用 find_if 修改指定项；再解释为什么 push_back 之后不该不加判断地继续使用之前保存的引用。

7. 模板与现代标准：学到能读懂库即可

7.1 模板把“类型”变成参数

cpptemplate<typename T>
T choose_larger(T a, T b) {
    return a < b ? b : a;
}

调用 choose_larger(2, 5) 时实例化适用于 int 的版本。模板不是运行时自动更换类型；实际所需版本通常在编译阶段生成。

如果希望限制可接受类型，C++20 concepts 可以给出更准确的接口约束：

cpp#include <concepts>
template<std::integral T>
T twice(T value) { return value + value; }

这不等于防止数值溢出。约束类型和验证数值范围是两件事。通用服务器代码应在输入边界检查范围，不用模板技巧代替业务规则。

7.2 constexpr、枚举与命名空间

constexpr 允许在满足条件时进行常量求值，但不是任何一次调用都必然发生在编译期。enum class 将枚举值放在明确的作用域里，减少隐式转换。

cppenum class Status { pending, completed };
constexpr int max_page_size = 100;

namespace task 避免和其他库的 Task、Error 等名字冲突。头文件不要写全局 using namespace std;，否则所有包含它的文件都受影响。

C03. CMake 也是一种语言：参数、变量、列表、作用域

不把 C++ 和 CMake 语法混在一起

命令形式是 命令名(参数...)，不需要分号结束语句；# 开始注释。变量名常区分大小写，命令名不区分大小写。一般保持命令小写、自定义项目开关大写，帮助阅读。set(name value) 写变量，${name} 在参数中展开它。

文件：lessons/cmake/variables.cmake

  set(label "inner")

认识几类相似但不同的变量

条件与目录作用域

  message(STATUS "Extra logs enabled")

include 路径从哪里来

源代码写 #include "greeting/greeting.hpp"，因此搜索根应是 include，而不是 include/greeting。库自己的 cpp 需要此搜索根，应用在包含公开头时也需要，于是标为 PUBLIC。

关键字 当前 target 使用要求 消费当前 target 的目标得到要求
PRIVATE 有 不传播该编译使用要求
PUBLIC 有 有
INTERFACE 本目标不用 有

这张表用于理解 include、编译特性等使用要求。静态库的 PRIVATE 链接依赖可能仍需要传递到最终链接步骤，不能推导为“PRIVATE 的库绝不会出现在程序链接命令中”。编译使用要求与最终链接需要分别分析，详见 target_link_libraries 官方说明。

应用 target_link_libraries(greeting_app PRIVATE greeting) 获得 greeting 的使用要求，包括 include 和 C++20；PRIVATE 的意思是应用不再将这条依赖作为自己的公开接口向下传播，不是拒绝继承 greeting 的 PUBLIC 配置。

一个能真正观察差异的故障实验

在你复制的实验目录中，把 greeting 的 include 改 PRIVATE。库自己仍能编译，但 app 找不到 greeting/greeting.hpp，说明要求未传播。恢复 PUBLIC；重新 configure/build 应通过。不要为了救急给全局 include_directories 加所有路径，这会掩盖真实依赖。

把库改为 INTERFACE 不能直接“省略 cpp 编译”：普通有实现的 cpp 必须编译。header-only 库才可用 add_library(name INTERFACE) 包装 include 和特性。INTERFACE target 本身通常没有 .a/.lib 产物。

STATIC、SHARED、OBJECT 分别表示静态库、共享库、目标文件集合。共享库还涉及导出符号和运行时加载路径，尤其 Windows DLL；不能假设把 STATIC 改为 SHARED 后所有平台交付自然完整。本课程先把静态库链路做对。

练习：增加 goodbye 声明和实现并从应用调用。只改库 cpp 时，应用 cpp 通常不用重编译，但应用需要重新链接；改公开头可能导致库和应用都重新编译。用 --verbose 对照你的预测。

C07. 第三方依赖：源码、find_package、FetchContent 与包管理器

先识别你手中拿到的到底是什么

只有头文件的库常用 INTERFACE target；有 cpp/c 源码的库需要编译；预编译库需要与当前平台、架构、编译器 ABI 和运行库兼容。头文件能被找到不代表链接就会成功；链接成功也不代表运行时 DLL 一定能找到。

最终后端采用 vendored 源码：third_party 随项目附带，版本、许可证与摘要记录在 NOTICE 中。优点是离线和固定输入，代价是仓库变大、升级和漏洞跟踪由维护者负责。新学习项目不要一开始同时混用多个来源的同一个库。

cmake# 概念片段：已准备相应路径时才能使用
add_library(json_vendor INTERFACE)
target_include_directories(json_vendor SYSTEM INTERFACE "${CMAKE_CURRENT_SOURCE_DIR}/third_party/json")
target_link_libraries(my_app PRIVATE json_vendor)

SYSTEM 通常把该 include 作为系统头目录处理以减少外部警告，但不表示“安全可信”；my_app 必须已创建。INTERFACE 目标也通过 target_link_libraries 使用，因为这个命令表达的不只是 .lib/.a 链接，还包括使用要求。

find_package 搜索已提供的包配置

cmake# C09 的真实实验会安装并查找到这个包
find_package(TaskKit 1 CONFIG REQUIRED)
target_link_libraries(consumer PRIVATE TaskKit::taskkit)

CONFIG 模式找 TaskKitConfig.cmake / taskkit-config.cmake。Module 模式找 FindTaskKit.cmake，模块可能来自 CMake 自带或你设置的 CMAKE_MODULE_PATH。CMAKE_PREFIX_PATH 提供安装前缀搜索提示；TaskKit_DIR 则可指向具体 Config 文件所在目录。不要把前者指成 include 子目录后期待自动解决所有事情。

find_package 通常负责查找和加载使用信息，不等于默认联网安装软件。依赖提供器/包管理器集成可能改变查找流程，所以看清项目实际配置。优先消费库给出的 imported target，它能携带头路径、链接产物和依赖，不要手写几十个绝对 .a 路径。

vcpkg / Conan 的定位

包管理器解决依赖取得、版本与构建组合；CMake 继续描述自己工程的 target。以 vcpkg 为例，常在首次 configure 提供它的 toolchain 文件，并用 manifest 记录依赖；Conan 常产生可供 CMake 查找的配置和工具链。具体命令随版本变化，使用时查各自官方文档，不把一个历史安装脚本当普适真理。

在 Windows 上不要把 MSVC 编译的 C++ 库随意塞给 MinGW GCC，也不要混搭 32/64 位、不同 CRT 或不兼容标准库。静态/动态链接、运行库选择和许可证均要了解。C 接口也需要确认调用约定和 ABI，不代表所有二进制随便互换。

练习：从最终项目指出 httplib、json、sqlite 分别是哪种包装 target，找出哪个实际编译了 .c。参考：httplib/json 是 INTERFACE，sqlite3_vendor 是 STATIC；SQLite 源码使用 C 编译，因此 project 启用了 C 和 CXX。

文件：lessons/cmake/03_project/tests/title_test.cpp

cpp#include "taskkit/title.hpp"
#include <iostream>
#include <string>
int main() {
    int failures{};
    const auto check = [&failures](bool ok, const char* name) {
        if (!ok) { ++failures; std::cerr << "FAIL: " << name << '\n'; }
    };
    check(taskkit::valid_title("learn"), "ordinary title");
    check(!taskkit::valid_title(""), "empty title");
    check(!taskkit::valid_title(" \t"), "whitespace title");
    check(taskkit::valid_title(std::string(200, 'a')), "200-byte boundary");
    check(!taskkit::valid_title(std::string(201, 'a')), "201-byte boundary");
    check(taskkit::version() == "1.0.0", "configured version");
    return failures == 0 ? 0 : 1;
}

根目录 include(CTest) 提供 BUILD_TESTING 选项并在启用时打开测试支持。tests 子目录只有选项开启时才加入；add_test 注册一个测试，COMMAND title_test 引用可执行目标，让 CMake 处理平台后缀和配置路径。

测试程序有六个检查：普通标题、空串、纯 ASCII 空白、200 字节、201 字节和配置版本。失败时输出具体检查名字并返回非零。一个 CTest 条目可以包含多个内部检查，因此“1 个测试目标”与“6 项断言条件”不是同一统计。

powershellcmake --build build/cmake03 --target title_test

ctest --test-dir build/cmake03 -R title_rules --output-on-failure --no-tests=error
ctest --test-dir build/cmake03 -R title_rules -V

-N 列出但不运行；-R 按正则筛选；--output-on-failure 保留失败输出；-V 展示更详细的测试命令和输出。--no-tests=error 避免因为名字写错或没有注册测试而空跑成功。

做一个真能抓住错误的实验

在你复制的实验中把长度上限从 200 改成 199，重新 build/test。200-byte boundary 应失败；恢复后再通过。只运行 CTest 而不 build，可能还在测试旧程序，这正是本章要求你主动观察的陷阱。

Ninja 主线可通过 CMake Tools 选择项目与 preset，或让 clangd 指向相应 build 目录。不同时启用多个互相争夺补全和诊断的 C++ 语言服务器；具体设置按所用扩展文档选择。本教程提供命令行作为独立可验证的基准。

C09. install 与 export：让另一个项目只依赖安装结果

安装后复用的四种常见错误

一是只装 .a 不装头，编译阶段找不到声明；二是装了头但没写 Config/Targets，find_package 找不到包；三是导出接口仍包含开发者电脑上的源码绝对路径，换目录就坏；四是包被找到但 ABI 不兼容，编译/链接/运行仍可能失败。

C10. 生成器表达式、生成文件与构建依赖：理解执行时间

不同写法发生在不同时间

set、if 和 configure_file 在配置阶段工作；$<...> 生成器表达式在支持它的属性上下文中稍后求值；编译器、代码生成器和链接器由构建工具按依赖触发。不要在 configure 阶段读取一个只有 build 才产生的文件，然后疑惑它为什么不存在。

cmake# 片段：app 必须已经存在
target_compile_definitions(app PRIVATE "$<$<CONFIG:Debug>:APP_DEBUG=1>")

外层条件表达式在 Debug 配置生成 APP_DEBUG=1，其他配置为空，适用于多配置生成器。if(CMAKE_BUILD_TYPE STREQUAL "Debug") 只是配置时判断变量，对多配置工程无法表达同一个构建树的多种配置。

$<TARGET_FILE:task_server> 指向当前配置下的实际可执行文件路径，主后端的 Python HTTP 测试用它启动服务器。硬写 build/Debug/task_server.exe 会破坏 Linux、Ninja 和用户自定义输出路径。

configure_file 与构建时生成命令

版本号来自 CMake 变量时使用 configure_file 已够用。若需要根据 schema 调用生成器产出源码，应把输入、输出、命令和依赖纳入构建图。下面是进阶结构片段，tools/generate.py 和 schema.txt 是需要你自己实现的扩展输入，不是默认工程内已有文件：

cmakefind_package(Python3 COMPONENTS Interpreter REQUIRED)
set(generated_header "${CMAKE_CURRENT_BINARY_DIR}/generated/schema.hpp")
add_custom_command(
  OUTPUT "${generated_header}"
  COMMAND "${CMAKE_COMMAND}" -E make_directory "${CMAKE_CURRENT_BINARY_DIR}/generated"
  COMMAND "${Python3_EXECUTABLE}" "${CMAKE_CURRENT_SOURCE_DIR}/tools/generate.py"
          "${CMAKE_CURRENT_SOURCE_DIR}/schema.txt" "${generated_header}"
  DEPENDS "${CMAKE_CURRENT_SOURCE_DIR}/tools/generate.py"
          "${CMAKE_CURRENT_SOURCE_DIR}/schema.txt"
  VERBATIM)
add_custom_target(generate_schema DEPENDS "${generated_header}")
add_dependencies(app generate_schema)
target_include_directories(app PRIVATE "${CMAKE_CURRENT_BINARY_DIR}/generated")

OUTPUT 是实际产物；DEPENDS 指定输入变化时要重跑；VERBATIM 帮助正确转义命令参数，不是自动执行任意 shell 语法。生成脚本必须失败返回非零并且真的写出目标文件。漏掉 DEPENDS 会导致输入已改、产物却没更新；多个独立规则写同一个输出会造成并行竞争。

add_custom_target 本身通常总被认为需要构建，但本例的文件规则由 OUTPUT 的时间戳决定是否重跑。add_dependencies 建立目标顺序；target_link_libraries 还表达链接与使用要求，二者不能相互替代。语义可查 add_custom_command 官方文档。

公共头改变为什么会触发重新编译

编译器会给 Ninja 提供头文件依赖信息，实际包含某个头的源文件会受它变化影响。CMake 描述工程层依赖，编译器参与发现文本包含依赖；不是每次改头都全量编译所有项目，也不是不把头列在 sources 就永远检测不到。

不要在配置脚本中随意执行网络下载、改系统环境或修改源码树的副作用。一个可复现工程应尽量让源码是输入、构建树是输出；同一份源码可以对应 Debug、Release、不同工具链的多个构建树。

练习与参考：把 TaskKit 的版本改成 1.0.1，configure 后观察 generated 头，再 build。测试的版本契约也需相应更新。只改生成头会在下次配置时被模板覆盖，说明正确修改位置是 project VERSION 和对应测试预期。

8.2 把一个函数拆成静态库

加入 greet.hpp、greet.cpp，声明和定义一个 std::string greeting()，在 main 中打印它。CMake 改成：

cmakecmake_minimum_required(VERSION 3.24)

target_include_directories(greeting PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})
target_compile_features(greeting PUBLIC cxx_std_20)
add_executable(first_app main.cpp)
target_link_libraries(first_app PRIVATE greeting)

greeting 和 first_app 都是 target。target 是一组源文件、属性、依赖和使用要求组成的构建对象，不只是磁盘上的文件名。

当 first_app 链接 greeting 时，CMake 知道应先构建库，还能把库公开的 include 目录、所需语言标准传播给消费者。这就是现代 CMake 的核心工作方式。

8.3 PRIVATE、PUBLIC、INTERFACE 到底区别在哪

可见性 构建自己时使用 给依赖自己的 target 使用
PRIVATE 是 否，使用要求通常不传播
PUBLIC 是 是
INTERFACE 否 是

例如 task_core 的公开头文件位于 include，消费者必须能包含它，因此 include 路径是 PUBLIC。警告策略是项目自身开发要求，一般 PRIVATE，避免把你的所有警告强加给外部库使用者。

静态库有一个容易误解的细节：库本身不完成最终的可执行文件链接。它 PRIVATE 依赖的另一个库，最终仍可能作为“仅链接依赖”被带到可执行程序链接步骤中。这不代表那个库的所有编译使用要求都变成 PUBLIC。详见 target_link_libraries 官方语义。

8.4 为什么不用全局 include_directories

全局设置使后面的很多 target 隐式受到影响，规模一大很难解释哪个目标为什么能找到某个头文件。优先用 target_include_directories、target_compile_options、target_link_libraries 把要求贴到真正需要它的目标上。

不要对全部源码统一强加 -Werror，尤其不要把第三方源码警告当成自己的错误。项目对第三方包含目录使用 SYSTEM，减少外部头文件诊断对学习的干扰。

练习：把 greeting 的 include 改成 PRIVATE，分析 main 是否还因为文件恰好同目录而能找到头文件；再把公开头文件移进独立 include 目录观察区别。验收：能画出 first_app → greeting 的依赖，并解释标准和头文件路径从哪里传来。

9.2 编译选项、编译定义、链接选项

cmaketarget_compile_options(my_target PRIVATE -Wall -Wextra)
target_compile_definitions(my_target PRIVATE APP_FEATURE=1)
target_link_options(my_target PRIVATE -fsanitize=address)

这是命令形态示例，my_target 要先创建。compile options 控制编译阶段；compile definitions 定义 C/C++ 宏，代码里可以 #if APP_FEATURE；link options 控制链接器。不要把三者都揉成一长串全局 flags。

MSVC 不认识所有 GCC 参数，因此用 if(MSVC) 分支。项目的 GCC/Clang 警告包括 -Wconversion 和 -Wshadow；MSVC 使用 /W4、/utf-8 等。平台库同样分支：Windows socket 需要 ws2_32，线程依赖优先交给 Threads::Threads。

target_compile_features(... cxx_std_20) 要求至少支持 C++20。为了减少 GNU 扩展与标准 C++ 的差异，项目关闭 CMAKE_CXX_EXTENSIONS。

9.3 Debug、Release 与生成器

Ninja 是单配置生成器：一个构建目录主要对应一种配置，用 CMAKE_BUILD_TYPE 选择 Debug 或 Release。Visual Studio、Ninja Multi-Config 属于多配置生成器，通常在 build 时用 --config Debug 选择配置。

powershell# 本教程使用单配置 Ninja

cmake --build build/manual-debug --parallel 2

# cmake -S . -B build/vs -G "这里填写本机实际生成器名称" -A x64
# cmake --build build/vs --config Debug

Debug 便于观察变量和单步；Release 开启更多优化，代码行与实际执行顺序未必一一对应。性能测量使用 Release，错误定位常从 Debug 开始。

不要在同一个 build 目录来回切换 GCC 与 MSVC，或切换 Ninja 与 Visual Studio。换工具链时新建构建目录最容易理解。

9.4 CMake cache 是什么

构建目录内 CMakeCache.txt 保存检测结果与缓存变量，例如编译器位置。后来改 PATH，不一定使旧构建目录自动换编译器。可以先看缓存，或者用新目录验证。

powershellcmake -LA -N build/debug
cmake --build build/debug --verbose

第一条查看缓存，第二条显示实际编译/链接命令。把 IDE 里的“找不到头文件”与真正构建时的 include 参数对照，经常能迅速定位问题。不要手动改 Ninja 自动生成文件来修复项目，应改 CMakeLists。

先运行：

依次输入：

第二次 list 中任务 1 前应显示 [x]；删除后任务 2 不再出现。程序重启后数据消失，这是这个阶段只使用内存的预期结果。

11.2 手把手重写：先只有循环

先在自己的练习文件中只写 getline 循环，用 istringstream 读取命令词，识别 quit。能正常退出后，再加入 vector 和 next_id。不要一次把所有 if 分支都抄进去。

cppstd::vector<task::Task> tasks;
std::int64_t next_id = 1;
for (std::string line; std::getline(std::cin, line);) {
    std::istringstream input(line);
    std::string command;
    input >> command;
    if (command == "quit") break;
    // 逐步加入 add / list / done / delete
}

这是 main 内的中间状态；需要 domain.hpp、vector、string、sstream、iostream。完整可编译文件见 examples/03_cli.cpp。

11.3 再实现 add 和 list

std::getline(input >> std::ws, title) 会先略过前导空白，再读取剩下的一整段标题，因而标题可以含空格。先调用 title_error，通过后再 push_back 并递增 ID。

列表循环读取每个 Task，只打印，不修改，因此使用 const auto&。这个阶段可以不设计抽象接口，不要为了未来的可能需求先加入十层继承。

11.4 最后实现 done 与 delete

把参数读成 string，调用严格的 parse_id，再检查是否还有多余参数。查找时按 Task::id，而不是直接把 ID 当 vector 下标。删除后 ID 可能不连续，所以 tasks[id - 1] 是错误假设。

找到任务后：done 修改 completed；delete 调用 erase。删除之后就不要继续使用那个迭代器。

12. 网络基础：理解一次请求穿过哪些层

12.1 IP、端口、socket、进程

IP 用来定位网络中的主机或接口；端口帮助操作系统把流量交给相应的服务。127.0.0.1 是本机回环地址；服务器监听这个地址时通常只能由本机连接。0.0.0.0 作为监听地址表示监听所有 IPv4 接口，不是客户端应当访问的目标地址。

socket 是操作系统提供的通信端点。典型 TCP 服务器执行 bind → listen → accept → read/write；这些调用并不等于你的业务接口。cpp-httplib 把底层细节包装好，让本项目把精力集中到接口和资源管理。

12.2 TCP 是字节流，没有 JSON 消息边界

一次 send 不保证对端一次 recv 就能完整得到相同长度的数据。消息可能分段，也可能多次发送被一起读取。若直接编写 socket 协议，需要自行定义长度、分隔和部分读写处理。

HTTP/1.1 定义了请求行、头部、消息体以及消息长度等规则，成熟库负责解析。不要简单搜索 \r\n\r\n 后就假设收到了完整请求，也不要手写一个只认识 GET 的解析器后直接当公网 HTTP 服务器使用。

12.3 HTTP 消息长什么样

httpPOST /api/tasks HTTP/1.1
Host: 127.0.0.1:8080
Content-Type: application/json
Content-Length: 22

{"title":"Learn HTTP"}

这里展示的是逻辑文本，在线路上行结尾使用 CRLF；该 ASCII JSON 正好 22 字节。客户端工具会正确计算长度，不要手工把汉字数当 Content-Length。

httpHTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: /api/tasks/1

{"id":1,"title":"Learn HTTP","completed":false}

真实响应还会包含库生成的长度等头部。客户端通过状态码判断总体结果，通过 JSON 获得业务字段。

12.4 请求从入口到数据库

text客户端
  → TCP/HTTP 库
  → 请求体大小等限制
  → token 检查与路由匹配
  → JSON 类型和字段校验
  → TaskRepository
  → SQLite prepared statement
  → 结果转 JSON
  → HTTP 响应与日志

注意，有些错误在路由前就被库拒绝，这类响应不一定拥有应用层生成的 request ID。日志与监控设计需要接受这种边界。

12.5 幂等、重试与超时

GET 通常读取资源；POST 创建资源，重复提交可能产生重复任务；本项目 PATCH 是给字段赋值，重复相同操作通常得到相同最终状态；DELETE 重复后资源仍然不存在，虽然第一次返回 204、第二次返回 404，状态码不同不自动否定其幂等性。

客户端超时不能证明服务器没有完成写入。如果 POST 完成数据库提交后响应丢失，客户端盲目重试会创建第二个任务。需要可靠重试的系统应设计幂等键，并在数据库中对它加唯一约束。

练习：使用 curl.exe -v 访问 healthz，指出连接地址、请求头、响应头和 JSON 的位置。验收：能区分“连不上端口”“HTTP 404”“JSON 校验失败”。

13. 里程碑二：你的第一个 HTTP 服务

13.1 先只保留一条路由

examples/04_http.cpp 的关键代码：

cpphttplib::Server server;
server.Get("/healthz", [](const httplib::Request&, httplib::Response& response) {
    response.set_content(nlohmann::json{{"status", "ok"}}.dump(), "application/json");
});
return server.listen("127.0.0.1", 8081) ? 0 : 1;

Get 注册一个处理 GET 的回调；注册阶段不会立刻处理请求。listen 开始监听并进入服务循环，通常会阻塞当前主线程。服务器运行期间终端没有出现新的命令提示符，是正常现象。

库使用阻塞 I/O 与线程池，主要支持 HTTP/1.1；本教程据此设计小规模 API，不将它解释为无限并发框架。见 cpp-httplib 官方介绍。

cppnlohmann::json result = {{"title", "a \"quoted\" task"}, {"completed", false}};

dump 负责引号转义等编码工作。不要直接拼接 "{\"title\":\"" + user_input + "\"}"，用户标题包含引号时会破坏 JSON。

14. 在编码前写清 API 契约

14.1 创建、更新与列表的输入输出

创建只接受一个字段：

json{"title":"Learn SQLite"}

标题需要 1～200 个 UTF-8 字节，不允许 ASCII 控制字符和纯 ASCII 空格。服务器生成 id，并将 completed 初始化为 false。客户端不能自己指定 id 或偷偷提交 admin 等额外字段。

更新允许下列任意非空组合：

json{"completed":true}

json{"title":"Learn transactions","completed":false}

空对象、未知字段、字符串 "false"、null 都不符合契约。缺少 completed 表示保持原值；显式 false 表示改成未完成。

列表默认 limit=20，最大 100；offset 默认 0，范围 0～1,000,000。按 id 升序返回：

json{"items":[{"id":1,"title":"Learn SQLite","completed":false}],"limit":20,"offset":0}

分页参数必须完整解析成整数，重复 limit/offset 被拒绝。当前版本忽略其他未知查询参数。若希望 typo 也返回 400，可以作为契约强化练习，修改后同步更新测试。

14.2 状态码与统一错误体

状态码 本项目含义 示例
200 成功读取或修改 GET、PATCH
201 成功创建 POST
204 成功删除且没有响应体 DELETE
400 JSON 语法、路径 ID 或分页格式错误 1x、残缺 JSON
401 配置 token 后鉴权失败 缺 Authorization
404 路径或任务不存在 GET 已删除 ID
413 请求体超过 16 KiB 过大的 JSON
415 Content-Type 不接受 text/plain
422 JSON 合法但字段不符合约束 空标题、错误布尔类型
500 未预料的服务端错误 数据库故障
503 SQLite 暂时忙或锁定 等待后仍无法获得锁 
json{"error":{"code":"validation_error","message":"title must be a string"}}

message 给人看，code 适合客户端程序判断。不要让客户端靠匹配某一句自然语言错误文本来实现业务逻辑。

14.3 为什么要限制请求

一个任务标题只有 200 字节，允许无限大的 HTTP body 没有意义。最大 body、线程数、队列长度、读写超时共同限定服务器愿意投入的资源。队列满时底层库可能直接关闭连接，不能保证一律得到 JSON 503。

本项目使用库的默认 JSON 重复键处理策略，重复字段通常保留后出现的值；它没有实现“所有重复 JSON 键一律拒绝”。需要严格金融协议、签名消息等场景时，应额外设计确定的解析规则。这是契约细节，不要留给客户端猜测。

练习：先在纸上写出 POST {"title":123} 应返回什么，再找代码中的校验位置。验收：不能只描述正常请求；每个输入边界都有明确结果。

15. SQL 与 SQLite：让数据跨越进程生命周期

15.1 SQLite 是嵌入式数据库

本项目把 SQLite 编译进程序，数据库主要保存在一个文件中，不需要先启动独立数据库服务。它适合教学和很多单机应用；未来高并发、多节点共享状态等需求需要重新评估数据库和部署结构。

关系型数据库把任务存成一张表，每行一个任务，每列一个字段：

sqlCREATE TABLE IF NOT EXISTS tasks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL CHECK(length(CAST(title AS BLOB)) BETWEEN 1 AND 200),
  completed INTEGER NOT NULL DEFAULT 0 CHECK(completed IN (0,1))
);

PRIMARY KEY 唯一标识一行；NOT NULL 禁止缺值；CHECK 限制列的合法范围。应用层和数据库层都做必要验证，能防止以后其他写入路径绕过应用规则。

这里 CAST 为 BLOB 是为了按字节计数，与 API 的 200 字节约束一致。AUTOINCREMENT 减少已提交历史 ID 的重用，但不保证 ID 连续，且有额外开销；用户不可把它当作任务总数。

15.2 先认识 CRUD 对应的 SQL

sqlINSERT INTO tasks(title) VALUES('Learn SQL');
SELECT id,title,completed FROM tasks ORDER BY id LIMIT 20 OFFSET 0;
SELECT id,title,completed FROM tasks WHERE id=1;
UPDATE tasks SET completed=1 WHERE id=1;
DELETE FROM tasks WHERE id=1;

WHERE 限制操作范围。忘写 WHERE 的 UPDATE/DELETE 会影响全部行，所以在自己的练习数据库中操作。SELECT 的结果顺序需要显式 ORDER BY；不要依赖当前偶然看到的顺序。

15.3 预处理语句与参数绑定

程序中的 SQL 应写成：

sqlINSERT INTO tasks(title) VALUES(?1);

再用 bind 把标题作为数据传入。若标题是 x'); DROP TABLE tasks; --，它仍应存成普通文本，而不是被解释为新的 SQL。

占位符适用于值，通常不能直接代替表名、列名或排序方向。动态排序字段必须从允许列表中选择，不能把任意客户端字符串拼进 SQL 标识符位置。

15.4 事务解决“多步必须一起成功”

单条 INSERT/UPDATE/DELETE 自身具有事务语义。若未来创建任务后必须同时写一条审计记录，应该：

sqlBEGIN IMMEDIATE;
INSERT INTO tasks(title) VALUES(?1);
INSERT INTO audit_log(task_id,action) VALUES(?2,'created');
COMMIT;

中间失败则 ROLLBACK。这段是扩展设计示意，当前项目没有 audit_log 表，不要直接对附带数据库执行。事务应尽量短；不要在持有数据库写事务时请求远程 HTTP 服务。

ACID 中的原子性关心整体成功或整体失败；隔离性关心并发事务彼此如何可见。数据库保证不能替你定义业务上“允许哪一种更新覆盖哪一种”的规则。

15.5 WAL、锁与忙等待

本项目启用 WAL。它允许许多情况下读与写更好地并行，但 SQLite 仍不是多个写者可以无限同时写入的数据库。WAL 文件和共享内存文件与主库一起参与运行；不要在服务运行时只复制 .db 就认定备份完整。机制见 SQLite WAL 文档。

sqlite3_busy_timeout(..., 3000) 让某些锁冲突先等待一段时间，仍无法获得锁时再报忙。它不是“给所有数据库操作设置总执行时间 3 秒”。参阅 busy_timeout 接口。

16. 手把手实现数据库仓库

16.1 仓库只处理任务存取，不接触 HTTP

先看 include/task/repository.hpp 的接口：create、list、get、update、erase。这里没有 HTTP 状态码，没有 request/response，没有 JSON。将来换一个命令行入口，也可以继续使用这个仓库。

get/update 返回 optional，表达“找不到”；erase 返回 bool，表达是否删到行；数据库错误抛 DatabaseError。只有非常小的一层负责将数据库错误转换成 HTTP。

16.2 从连接构造开始

构造函数按这个顺序做事：

  1. sqlite3_open_v2 打开数据库。
  2. 立刻把 raw 句柄交给 db_，确保后续失败也释放资源。
  3. 检查打开结果，失败时抛异常。
  4. 设置 busy timeout、WAL、外键检查。
  5. 执行建表语句。

SQLITE_OPEN_FULLMUTEX 是 SQLite 自身的连接串行化选项。我们还使用仓库互斥量，让一次完整仓库操作成为应用层的临界区。它们所保护的边界并不完全相同。

16.3 写一个只能安全释放的 Statement

内部 Statement 把 sqlite3_stmt* 装进 unique_ptr。构造时 prepare；bind 时检查返回码；row 时区分 SQLITE_ROW、SQLITE_DONE、其他错误；析构时 finalize。

你应先只实现 prepare → step → finalize，执行 SELECT 1；再补 bind 与 Task 映射。这样每加入一个能力都有很小的验证范围。

不要在 sqlite3_column_text 返回内部指针后就立刻析构 statement，再返回该指针。当前 task() 会在 statement 仍有效时复制成 std::string，因此返回的 Task 独立拥有标题。

16.4 bind_text 的最后一个参数关乎生命周期

cppsqlite3_bind_text(stmt, 1, value.data(), static_cast<int>(value.size()), SQLITE_TRANSIENT);

SQLITE_TRANSIENT 要求 SQLite 在调用返回前复制数据，原 string 后来变化不会让 SQLite 继续引用失效内存。相对地，SQLITE_STATIC 要求调用者保证更长时间的数据有效性，不能随便用。参阅 SQLite 参数绑定文档。

这里长度转 int 的前提是标题已经限制到 200 字节。若封装用于任意大数据，必须先检查大小，不应无条件窄化。

16.5 create：先验证，后加锁，再执行

创建 SQL 使用 RETURNING，写入并获得 id/title/completed。取得一行后仍继续 step 到 DONE，确保写语句完成且提交阶段错误有机会被发现，再返回任务。

cppStatement stmt(db_.get(), "INSERT INTO tasks(title) VALUES(?1) RETURNING id,title,completed;");
stmt.bind(1, title);
if (!stmt.row()) throw DatabaseError(SQLITE_ERROR, "insert returned no task");
auto result = stmt.task();
(void)stmt.row();
return result;

这段位于持锁的方法内部，相关定义见完整源码。现代 SQLite 支持 RETURNING；本教程固定的版本符合要求。不要仅把“拿到一行”误解为所有数据库工作都完成。

16.6 update：缺省字段保持原值

sqlUPDATE tasks
SET title=COALESCE(?1,title), completed=COALESCE(?2,completed)
WHERE id=?3
RETURNING id,title,completed;

没提供的字段绑定 SQL NULL；COALESCE 选第一个非 NULL 值，因此保留原列。提供 false 时绑定整数 0，0 不是 NULL，所以能正确更新。

这把字段更新放在一条 SQL 中，不需要先 SELECT 再 UPDATE。两个请求同时改不同字段时，避免应用层“读取旧整行再整行覆盖”的典型问题。不过两个请求同时改同一个字段，仍是后写覆盖前写；这不是具备版本冲突检测的乐观锁系统。

16.7 list 和 erase 的细节

list 严格限制分页范围，然后循环 SQLITE_ROW 收集结果直到 DONE。erase 执行删除后使用 sqlite3_changes 判断是否影响了一行，并把整个过程放在同一把锁内，避免别的操作抢先改变连接的 changes 状态。

重写任务：在自己的分支按“构造连接 → list → create → get → update → erase”实现，每完成一步跑 core_tests。验收：能指出所有资源的拥有者、所有释放位置，以及为什么异常发生后锁不会一直占着。

17. 手把手把数据库接到 HTTP

17.1 先做没有输入的 healthz

在 main 创建仓库和 server，然后调用 register_routes(server, repository, token)。注册函数只是配置路由，真正监听仍由 main 负责。你可以先只注册 healthz，编译运行成功，再逐条打开其他路由。

这样拆分后，main 负责进程层面的启动与退出；http_api.cpp 负责协议适配；repository.cpp 负责存储。文件数量来自职责差异，不是越多越专业。

17.2 再实现序列化函数

cppJson as_json(const Task& value) {
    return {{"id", value.id}, {"title", value.title}, {"completed", value.completed}};
}

不要把数据库实现细节直接暴露出去。例如将来新增内部审计字段，不应该因为“把所有成员自动转 JSON”就意外暴露给 API 客户端。这里明确列出对外字段。

respond 统一设置 HTTP 状态码和 JSON Content-Type；fail 在它上面构造统一错误结构。减少路由间出现某条返回 JSON、某条返回裸字符串的不一致。

17.3 实现 body_object：语法合法不等于业务合法

完整顺序是：检查 Content-Type → 解析 JSON → 确认顶层是 object → 检查字段集合 → 检查字段类型 → 检查取值范围。

cppauto body = Json::parse(request.body, nullptr, false);
if (body.is_discarded()) {
    throw HttpError(400, "invalid_json", "request body is not valid JSON");
}
if (!body.is_object()) {
    throw HttpError(422, "validation_error", "request body must be a JSON object");
}

这里 false 表示解析语法错误时使用 discarded 结果，而不是按默认方式抛解析异常；它不能承诺“任何情况下绝不抛异常”，例如内存分配仍可能失败。具体选项见 JSON parse 文档。

访问字段先 contains、再 is_string 或 is_boolean，再 get。不要直接把所有输入都 get<std::string>() 然后把类型异常误判为服务器 500。

17.4 先接列表，再接创建

列表路由解析分页，调用 repository.list，把每个 Task 转成 JSON 并放进 array。空列表必须是 []，不要不小心构造成 null。

创建路由调用 read_title 验证，再执行 repository.create。数据库成功之后才设置 201 和 Location。输入验证失败时不能先写库再试图“撤销”。

cppconst auto value = repository.create(read_title(body));
response.set_header("Location", "/api/tasks/" + std::to_string(value.id));
respond(response, 201, as_json(value));

先通过 POST 新建，紧接着 GET 列表，应看到刚写入的数据。这个验收能同时覆盖网络、JSON、数据库和序列化。

17.5 读取、修改与删除

使用 "/api/tasks/:id" 路由参数，从 request.path_params 取出 id 字符串，再调用 parse_id。不要用匹配字符串直接参与 SQL 拼接。

GET 找不到返回 404；PATCH 把 JSON 映射到 TaskPatch，再调用 update；DELETE 成功设置 204，不再追加 JSON body。

写 generic lambda 时，复杂的依赖类型有时需要 template 消歧。本项目对解析后的 body 明确写 const Json body，让类型直观、避免初学者在 get<bool>() 的模板解析细节上停住。现代 C++ 并不要求能用 auto 的地方全部都写 auto。

17.6 最后接异常边界和日志

仓库抛出的异常穿过路由后，由统一 exception handler 转成响应。HttpError 保留明确的客户端错误；DatabaseError 把忙/锁定映射到 503；未知故障返回笼统 500。

客户端不需要知道你的数据库绝对路径、内部 SQL、服务器安装目录。内部日志可记录诊断码；生产系统可以在受控日志中保留更多异常上下文，但也要过滤 token、密码和请求中的隐私数据。

exception handler 必须考虑 catch (...)，因为 C++ 可以抛出非 std::exception 类型。第三方库行为随版本变化，不能假设任何回调异常都在任意版本中以相同方式处理。相关接口见 cpp-httplib 官方仓库。

17.7 主程序对象的顺序也是设计

main 先构造 repository，再构造 server，再构造退出观察线程。离开作用域时顺序反过来：先结束观察线程，再销毁 server，最后销毁仓库。

这让 server 内捕获 &repository 的回调不会正常地活得比 repository 更久。理解这个顺序后，你就知道这里不用把数据库仓库胡乱改成 shared_ptr。

验收：不看答案，画出 POST 的调用链；把标题上限改成 120 字节时，能列出需要同步修改的校验、数据库约束、文档和测试。

19. 并发：先证明正确，再追求吞吐量

19.1 两个请求可能同时执行

cpp-httplib 的工作线程可以同时调用不同路由。两个线程同时读写同一个没有同步保护的 vector、字符串或计数器，可能产生数据竞争，结果不只是“偶尔数字不对”，而可能是未定义行为。

最开始可以通过一把互斥量保护共享数据，先建立清晰的正确性边界。本项目仓库的方法在访问单一 SQLite 连接时都持有同一把 mutex。

19.2 锁住一项完整操作

cppstd::lock_guard lock(mutex_);
// prepare → bind → step → 读取结果/changes

如果只在 sqlite3_step 外面加锁，其他线程仍可能在你读取连接相关状态之前执行自己的语句，破坏应用假设。锁的范围要围绕需要保持一致的操作设计。

代价是仓库访问被串行化。线程池不是“数据库并行写入器”；一把锁加一个连接的方案有明确扩展上限。对于学习和小应用，这个限制换来了容易检查的行为。

19.3 原子变量解决很小的共享状态

请求 ID 计数器使用 atomic 的 fetch_add。这里要求的是不重复分配进程内递增号码，不是用计数器发布其他对象状态，因此 relaxed 顺序足够。它不是跨进程、跨重启全局唯一的追踪 ID。

不要把任意数据结构里的所有字段都改成 atomic 就认定整体线程安全。余额扣减、库存与订单关联等问题需要组合不变量，可能涉及锁或数据库事务。

19.4 jthread 管理线程生命周期

std::jthread 析构时请求停止并 join，降低忘记 join 导致的问题。stop_token 是协作式停止请求，线程代码要主动检查，不是强行在任意指令中断线程。

本项目独立线程每 100 毫秒检查退出标志，看到标志后在正常线程上下文里调用 server.stop。信号处理函数只设置保证无锁的 atomic，通过 static_assert 检查这一前提。不要在信号处理函数里打印日志、分配内存、拿 mutex 或直接调用复杂的停止流程。

19.5 停止不等于瞬间结束所有请求

server.stop 停止监听；库关闭队列时仍可能等待已有工作结束。读写超时、数据库忙等待和外部服务调用都会影响退出时间。systemd 或容器的停止宽限时间应与这些上限相配。

本项目没有实现严格的全局请求截止时间和完整 draining 状态机；Linux 上 SIGTERM 路径仍需在部署环境实际验证。不要把 Windows 上结束进程的测试当成 Linux 优雅停机已经被验证。

19.6 以后怎样扩展

先测数据库锁等待和查询延迟。如果瓶颈在串行数据库访问，可以评估多个连接、读写分离策略或 PostgreSQL；如果瓶颈在大量等待网络连接，可以研究事件循环和异步 I/O。不要同时引入连接池、协程和无锁队列，再试图猜哪一项导致 bug。

假设你发现 {"completed":false} 被忽略：先添加“true → false”测试，确认旧代码失败；再修复判断 optional 的逻辑；最后运行全部测试。这样错误不会在未来重构时悄悄回来。

不要只写“实现调用了哪个私有函数”这种紧贴实现的测试。更有价值的是外部可观察结果：字段是否变更、状态码是否正确、数据库是否保留数据。

20.5 CI 是同一组命令在干净环境再执行

附带 .github/workflows/ci.yml 展示 Ubuntu 构建、测试和 sanitizer 构建。把项目放到自己的 GitHub 仓库后，push/PR 触发工作流。文件出现在本地不代表已经在 GitHub 跑过；本次交付没有创建仓库或远程执行 CI。

首次上 CI 失败时，重点检查是否遗漏提交依赖文件、是否写死本机路径、是否混用大小写。Windows 文件系统上碰巧能找到 Task.hpp，Linux 上未必能找到实际名为 task.hpp 的文件。

练习：把标题上限临时改成 10，让一个预期合法的边界测试失败，再恢复。验收：能解释失败测试是在验证需求，而不是只是为了得到“全绿”。

21. 日志、配置、鉴权与后端的边界

21.1 可检索日志比随手打印更有价值

json{"method":"POST","path":"/api/tasks","status":201,"request_id":"12"}

实际键顺序可能不同。JSON 转义能避免客户端路径里特殊字符伪造新日志行；osyncstream 让多个线程的整条输出更容易保持完整。本项目没有记录请求 body 和 Authorization。

目前日志没有持久日志轮转、精确请求耗时和跨服务追踪。扩展时加入时间戳、耗时、服务版本和相关 ID；可以交给 systemd journal 或容器日志系统收集。不要把所有数据库错误都只记成没有上下文的“failed”。

21.2 healthz 与 readyz 区别

healthz 返回进程仍可处理基本请求。本项目没有访问数据库来做 healthz，因此它不证明数据库可写。

以后可以增加 readyz，在极小开销下检查当前是否愿意接业务流量。读检查也不能证明下一次写一定成功。健康检查本身应快、少分配、不会因为探测频繁制造更大负载。

21.3 Bearer token 的实际用法

在终端 A 生成随机 token：

powershell$env:APP_TOKEN = (python -c "import secrets; print(secrets.token_urlsafe(32))").Trim()

在安全的位置临时保存这个值后启动服务。终端 B 不会自动继承已经打开的终端 A 的新环境变量；用你刚才保存的相同值设置 $token：

powershell$token = '这里填你生成的值'
$headers = @{ Authorization = "Bearer $token" }
Invoke-RestMethod -Uri 'http://127.0.0.1:8080/api/tasks' -Headers $headers

缺失或错误 token 返回 401。任何得到 token 的人都可以操作全部任务，所以它适合单用户或受控服务调用，不提供用户身份隔离。源码中的普通字符串比较也不是经过侧信道审计的认证模块；有更严格要求时交由成熟身份系统和密码库处理。

21.4 登录功能为什么是一条独立主线

真正多用户系统至少要处理用户唯一标识、密码哈希、会话/令牌签发和撤销、登录失败限制、授权、用户禁用、凭据轮换。

密码不能明文存储，也不能仅用普通 SHA-256 当密码存储方案。应使用成熟库的专用密码哈希实现，例如 Argon2id，并按库的当前官方指引配置。这里不手写密码算法，也没有声称已实现登录功能。

最关键的授权查询应形如 WHERE id=? AND owner_id=?，owner_id 来自服务端验证过的会话，而不是用户提交的 JSON。否则攻击者换一个任务 ID 就可能访问别人的数据。

21.5 CORS、CSRF 和 HTTPS 各解决不同问题

CORS 是浏览器跨源访问规则，不是服务端身份认证；curl 不会因为你没配 CORS 就停止发送请求。使用 cookie 自动携带凭据的浏览器应用还要考虑 CSRF。Bearer token 放 Authorization 的调用方式有不同风险面，依然需要妥善存储 token 并防止 XSS 泄露。

TLS/HTTPS 保护传输，反向代理负责证书和外部连接；它不会自动判断用户是否拥有某条任务。公网部署章节使用 HTTPS + token，但这仍是单用户服务。

练习：在不带 token 的情况下请求 healthz 和 api/tasks，解释为什么一个成功一个失败。验收：能区分认证“你是谁/凭据是否有效”和授权“你能操作哪条数据”。

22. 性能与排错：先测量，再决定改哪里

22.1 三个基础指标

吞吐量表示单位时间完成多少请求；延迟表示单次请求耗时；错误率表示多少请求失败。只看平均延迟会隐藏慢请求，因此常看 p50、p95、p99。

p95=80ms 可以理解为这次采样中大约 95% 的请求延迟不高于这个值。它不意味着所有时间、所有用户都保证在 80ms 内完成。样本数、请求种类、并发数和客户端能力都会影响结果。

22.2 运行附带的小型负载工具

使用 Release 构建启动服务器，再在另一个终端：

powershellpython scripts/load_test.py --url http://127.0.0.1:8080/healthz --requests 200 --workers 8
python scripts/load_test.py --url 'http://127.0.0.1:8080/api/tasks?limit=20' --requests 200 --workers 8

如果 API 开启了 token，当前客户端终端也要设置相同 APP_TOKEN。脚本统计成功请求吞吐量及成功请求延迟，同时单独报告错误数。发生错误时不要只把成功样本的低延迟拿来宣传性能。

该脚本每次请求新建连接，使用 Python 线程，本机客户端与服务器还可能竞争 CPU，因此它是观察趋势的学习工具，不是正式容量评估。不要把 healthz 的数字当成复杂数据库业务吞吐量。

22.3 逐项定位瓶颈

按 workers=1、4、8、16 依次测同样的请求，记录错误率和 p95。每次只改一个因素。若线程数增加但吞吐没有提高，可能是数据库锁串行化；若 CPU 很高，可能是序列化或查询；若大部分时间等待 I/O，增加 CPU 未必有效。

数据库慢查询先看条件、排序和索引。SELECT ... ORDER BY id 已可利用主键顺序。给每一列都加索引会增加写入和存储成本。增加索引前用 EXPLAIN QUERY PLAN 观察查询计划。

22.4 一套从外向内的排错路径

  1. 客户端使用的地址、端口、HTTP/HTTPS 是否正确。
  2. 进程是否存在，启动日志是否报错，端口是否监听。
  3. healthz 是否成功；API 是否需要 token。
  4. 状态码属于协议错误、输入错误、缺失资源还是内部故障。
  5. request ID 能否关联到对应日志。
  6. 数据库路径、目录权限、锁等待、磁盘空间是否正常。
  7. 最小复现能否写成测试。

Windows 可用 Get-NetTCPConnection -LocalPort 8080 -ErrorAction SilentlyContinue 查看监听情况；Linux 用 ss -ltnp。看到占用端口的进程后先确认它是谁，不要随手结束不认识的服务。

验收：写下同一接口在两种并发数下的结果、环境和一个待验证假设；没有数据时不宣称“提高了十倍性能”。

23.4 反向代理与 HTTPS

按 Caddy 官方安装说明 安装，编辑 /etc/caddy/Caddyfile，将附带示例中的 api.example.com 替换为你真正拥有并配置的域名：

上面的 .example 只是占位，不能申请真实证书。配置真实域名后：

24. Docker：把构建与运行环境写成文件

24.1 镜像和容器不是一回事

镜像是程序和环境的打包模板；容器是基于镜像启动的进程环境；volume 保存不应随容器替换而消失的数据。

Dockerfile 使用两个阶段：build 阶段安装编译器并运行测试；runtime 阶段只放运行库和可执行文件。多阶段构建的机制可查 Docker 官方说明。

这里固定 ubuntu:24.04，但发行版标签内的软件更新仍会变化。严格可重复交付还需固定镜像 digest、管理系统包来源并记录构建环境；当前文件并不声称实现位级可重复构建。

24.2 先准备 Docker 引擎，再运行命令

确认 docker version 和 docker compose version 可用。Docker 安装涉及系统虚拟化和服务配置，使用其官方安装文档，不由本教程自动修改你的系统。

PowerShell，在项目根目录：

powershell$env:APP_TOKEN = (python -c "import secrets; print(secrets.token_urlsafe(32))").Trim()
docker compose up --build -d
docker compose logs --tail 100 api
curl.exe -i http://127.0.0.1:8080/healthz

bash 只需要把第一条换成：

bashexport APP_TOKEN=$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')

24.3 理解两处监听地址

容器内 APP_HOST=0.0.0.0，让 Docker 转发进来的连接到达应用；宿主机端口映射写 127.0.0.1:8080:8080，只让宿主机本地访问该端口。二者属于不同网络命名空间，并不矛盾。

宿主机上运行的 Caddy 可以代理到这个映射端口。如果 Caddy 也放在另一个容器，不能继续把 127.0.0.1 当作 api 容器地址，需要使用共享 Docker 网络与服务名，这属于另一个部署拓扑。

24.4 持久化与停止

powershelldocker compose down
docker compose up -d

compose.yaml 使用 named volume，普通 down 后该卷仍保留。不要为了“清理”加入删除卷的选项，除非明确要删除数据库。

容器通过非 root 用户运行；新的命名卷使用镜像中 /data 的初始权限。已有卷若权限不匹配会报无法打开数据库，应确认卷所有者与 UID=10001，而不是把目录权限一律改成 777。

此项目没有定义 Docker HEALTHCHECK。需要编排系统健康状态时，应单独设计探测工具或由外部系统访问 healthz；不能因为有 healthz 路由就说 Docker 已经执行健康检查。

验收：创建一条任务 → down → up → 原任务仍存在。再看镜像中没有整个编译工具链，理解多阶段构建为何有用。

25.3 为什么 CREATE TABLE IF NOT EXISTS 不是迁移系统

原来任务只有 title/completed，后来增加 priority。即使你把建表语句改了，已经存在的旧表也不会自动长出新列。

迁移需要记录数据库当前版本，并按顺序执行一次性变化。例如版本 0 → 1：

sqlBEGIN IMMEDIATE;
ALTER TABLE tasks ADD COLUMN priority INTEGER NOT NULL DEFAULT 1 CHECK(priority BETWEEN 0 AND 2);
PRAGMA user_version=1;
COMMIT;

这段是本教程下一章毕业练习的迁移，不是当前程序启动时自动执行的功能。重复执行 ALTER 会失败，因此不能每次启动无条件执行。脚本示例 scripts/migrate_priority_example.py 先检查版本，在事务内执行并验证列。

在停止服务并备份后的学习数据库上运行：

powershellpython scripts/migrate_priority_example.py tasks.db
python scripts/migrate_priority_example.py tasks.db

第一次输出 Schema migrated: 0 -> 1，第二次输出 Schema already at version 1。这只证明 schema 迁移完成；要让 API 返回 priority，还需要完成下一章的 C++ 修改。

增加列、改变约束、删除列的能力和限制不同，具体操作先查 SQLite ALTER TABLE 文档。更复杂迁移可能要建新表、复制数据、重建索引并检查外键。

25.4 一个可执行的发布顺序

先在副本数据库上测试迁移与新应用；做并验证备份；停止或控制写入；执行迁移；部署新程序；检查健康与关键接口；观察错误率和日志。

代码回滚不等于数据库回滚。新版本写入了旧版本不认识的数据后，简单把旧 EXE 换回来可能不够。尽量采用能兼容一段时间的 schema 变化，并明确哪些迁移不可逆。

验收：从一份备份启动成功；能回答“如果刚升级的程序启动失败，数据怎样恢复”。

26. 毕业任务：独立添加 priority，而不是再抄一遍 CRUD

这个任务把语言、CMake、SQL、HTTP 和测试串起来。先阅读需求与验收条件，再关闭答案部分自己实现。

26.1 需求

Task 新增整数 priority，允许 0、1、2，默认 1。创建时可省略；PATCH 可以只修改 priority；列表新增可选过滤 ?priority=2，仍按 id 升序并支持分页。旧数据库必须迁移，旧任务默认 priority=1。

需要通过的行为：创建省略字段返回 1；显式传 0/2 保存成功；传 -1、3、1.5、"1"、true、null 返回 422；PATCH 只含 priority 合法；过滤只返回相应任务；重启后仍存在；迁移执行两次不会重复添加列。

26.2 分解工作，而不是同时改十个文件

  1. 数据模型：Task 加 int priority{1}，TaskPatch 加 std::optional<int> priority。
  2. 数据库：先备份，再迁移旧表，并为新数据库设计相同字段。
  3. 仓库：所有 SELECT/RETURNING 补列，Statement::task 正确读列，create/update/list 传递 priority。
  4. HTTP：明确 JSON 整数类型和范围，允许创建可选字段，扩展 PATCH 非空判断与字段允许列表。
  5. 测试：旧功能仍通过，加新规则和迁移用例。
  6. 文档：更新示例 JSON、接口契约与 README。

注意 JSON 布尔不是这里想要的整数；不要因为 C++ 中 bool 能转 int 就接受 true。还要拒绝超出 int 范围的巨大 JSON 整数，先比较 JSON 数值允许范围或使用安全转换策略。

26.3 提示与参考设计

如果过滤参数缺省，可让仓库接收 std::optional<int> priority。SQL 使用固定语句与绑定参数：

sqlSELECT id,title,completed,priority FROM tasks
WHERE (?1 IS NULL OR priority=?1)
ORDER BY id LIMIT ?2 OFFSET ?3;

数据量增大后评估这个可选条件对查询计划的影响，必要时拆成两条固定 SQL。不要只为了少写一条语句而忽略索引效果。

更新可以延续 COALESCE；priority=0 不是缺省，也不是 NULL。与 optional 相同，判断的是 optional 是否有值，而非内部整数是否非零。

创建原本要求 body.size()==1，需要修改字段允许规则；只加读取 priority 的代码却忘记调整这个入口，会让所有带 priority 的 POST 都被旧校验拒绝。

26.4 独立完成的定义

从空文件夹重建一个类似项目，不必记住每个 API 名，但能查官方文档并解释选择；别人给出一个失败请求，你能复现、定位到一层并写回归测试；增加字段时知道它影响存储、协议、错误处理和已有数据。

做到这些，你已经从“写一些 C++ 代码”走到“能独立交付一个小型后端服务”。这比会背很多零散语言特性更接近工程能力。

27. 后续扩展路线：按真实需求继续学习

27.1 多用户与权限

先设计 users 表和 tasks.owner_id；所有任务查询基于服务端得到的用户身份过滤；再接入成熟会话/身份方案。密码存储的参数与方案参考 OWASP 密码存储指南，不要凭感觉实现。

验收要有两个用户 A/B：A 创建的任务 B 看不到，也不能通过直接改 ID 来删除。列表接口和单项接口都需要检查，不能只保护 UI 上的按钮。

27.2 PostgreSQL 与连接池

把仓库接口保留，替换底层实现。学习连接认证、事务隔离、prepared statement、连接池耗尽、连接断开后的恢复。不要把数据库连接放成一个毫无保护的全局对象。

可以从 PostgreSQL 的 libpq 官方接口 理解协议与结果管理，再按项目选择 C++ 包装库。迁移数据库不仅是改一个链接库名，SQL 方言、自增 ID、错误码和并发假设都需要重新验证。

27.3 乐观锁与分页演进

给任务增加 version，每次更新使用 WHERE id=? AND version=?，成功后 version+1，匹配不到时返回冲突。这解决多人编辑“后写默默覆盖前写”的问题，不能简单用内存 mutex 替代，因为客户端读取与提交之间可能隔了很久。

大 offset 查询可能越来越慢，数据变化时也容易跳项。可以增加 after_id 的游标分页：WHERE id>? ORDER BY id LIMIT ?。需明确稳定排序和游标含义。

27.4 异步网络与协程

在熟悉当前阻塞模型后，学习事件循环、非阻塞 socket、就绪通知、异步操作生命周期与取消。协程函数返回后，局部变量和捕获对象在何处存活是新的重点。

不要简单把每个同步方法加上 co_await 就认为架构自动升级。阻塞数据库调用若仍在事件循环线程里执行，整个循环照样被阻塞。需要将阻塞任务安排到合适的执行环境，并限制队列和并发。

27.5 缓存、后台任务与消息系统

只有测量说明数据库读取确实成为瓶颈时再加缓存，同时设计失效策略。只有请求中确实存在耗时任务时才拆后台执行，并定义任务状态、失败重试和幂等性。

不要第一版就同时引入 Redis、消息队列和微服务；每引入一个外部系统，就多出连接、超时、配置、部署和故障恢复问题。学习顺序应由业务需求推动。

27.6 进一步学习 CMake 工程化

将 task_core 变成可以安装给其他项目使用的库；学习 install(EXPORT)、包配置文件、命名空间 target、BUILD_INTERFACE/INSTALL_INTERFACE、版本兼容规则、交叉编译工具链文件。

本项目只是安装可执行文件，没有假装已经提供一个可复用的 CMake SDK。深入时从 CMake 官方教程 的安装、依赖发现与 target 章节逐步实践。

29.3 高频自检题与参考答案

为什么可以返回局部 string 的值，不能返回它的引用？ 返回值创建或传递一个由调用方拥有的结果，可能有拷贝消除；引用只指向已经结束生命周期的局部对象。

为什么数据库句柄用 unique_ptr 加自定义清理器？ 它不是用 new 分配的普通对象，需要 sqlite3_close_v2 释放；unique_ptr 表达唯一所有权并负责异常路径清理。

为什么 optional 中 false 仍算“有值”？ optional 的是否参与状态与内部 bool 值分别存储；has_value 判断字段是否提供，解引用后才是业务布尔值。

为什么 CMake 的 PUBLIC include 不是“把头文件公开到互联网”？ PUBLIC 只是构建依赖中的使用要求传播，与网络权限无关。

为什么 sql 参数绑定能防止标题变成 SQL？ SQL 结构先被解析，标题按数据参数绑定；它不会再次被当成 SQL 语法执行。动态表名等标识符仍需单独限制。

为什么一次 POST 超时后不能放心重试？ 数据库可能已经提交，只是响应没到客户端；没有幂等机制就可能重复创建。

为什么加了 shared_ptr 不代表线程安全？ 引用计数的并发管理不等于对象内容的并发读写安全，业务对象仍需同步。

为什么数据库开 WAL 仍加 mutex？ WAL 处理数据库层读写并发；mutex 保护本进程共享连接和一项完整仓库操作，职责不同。

为什么要测 Release？ 优化和 NDEBUG 等配置会改变程序及测试行为；Debug 通过不能替代 Release 验证。

为什么源代码跑通不等于部署完成？ 部署还需要运行身份、路径、环境变量、启动管理、网络入口、日志、备份和目标平台验证。
